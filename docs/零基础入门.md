## 第 0 章 先用一句话说清这个项目是什么

### 0.1 一句话

> **这是一台「自己会想办法的自动测试机」：你只给它一个网址和一句目标，
> 它自己去读接口文档、自己设计测试用例、自己发请求/开浏览器、自己判断哪里坏了、
> 最后写一份能直接看的 HTML 报告。**

### 0.2 用一个生活比喻

想象你雇了一个测试工程师来测你的网站。他每天做的事其实就四件：

| 他做的事 | 项目里的对应物 | 通俗解释 |
| --- | --- | --- |
| 读需求文档，想「我要测哪些点」 | **Brain（大脑）** | 决定测什么、怎么判断好坏 |
| 打开浏览器、发请求、点按钮 | **tools（工具层）** | 真正去「动手」的部分 |
| 按固定顺序干活：先规划 → 再执行 → 再分析 → 最后写报告 | **LangGraph 流程图** | 排班表，保证活儿按顺序干完 |
| 写一份测试报告交给老板 | **report（报告层）** | 把结果变成人能看懂的东西 |

所以整个项目的骨架就是：

```
大脑（决定测什么）  +  工具（真的去做）  +  流程图（按顺序串起来）  +  报告（说出来）
```

### 0.3 灵感的来源：为什么需要「会自己想办法」

传统的自动化测试是这样写的：

```python
def test_login():
    resp = requests.post("http://127.0.0.1:5001/api/login",
                         json={"username": "admin", "password": "123456"})
    assert resp.status_code == 200
```

问题在于：**每多一个接口，你就得多写一个函数**。接口从 10 个涨到 100 个，
测试代码也跟着涨十倍。人是跟不上的。

这个项目换了个思路：

> 不写「针对某个接口的测试」，而是写「**一个会读接口文档、并照着文档生成测试的脑袋**」。

文档（OpenAPI 规范）里写着「`GET /api/todos` 的 `status` 参数只允许 `active` / `done`，
传别的应该返回 400」。程序读到这句话，就自己生成一条用例：

```
用例 API-006：GET /api/todos?status=invalid  → 期望 400
```

这就是「Agent」（智能体）的含义：**不是把答案写死，而是把「怎么找答案」写成程序。**

### 0.4 这个项目测的是什么

它测两个东西：

1. **`demo_app/`** —— 一个故意做坏的待办清单网站（Flask 写的）。
   里面**故意注入了 9 个缺陷**（3 个 API 类 + 6 个 RAG 类），
   就等着 Agent 来发现。这是「有标准答案的考场」。
2. **外部第三方接口** —— 比如 Swagger 官方的 Petstore。
   用来证明这套东西不是只能测自己写的靶子（见 `docs/第三方契约验证.md`）。

> 为什么要有「标准答案」？因为只有知道正确答案，才能验证 Agent 的判断准不准。
> 这是测试领域的基本功：**测试代码本身也需要被验证。**

### 0.5 目录里最该先认识的 6 个文件

如果你只有 10 分钟，读这 6 个文件就够了（它们构成了主干）：

| 文件 | 一句话 |
| --- | --- |
| `agenttest/runner.py` | 总开关。命令行进来，起服务、建图、跑流程、打报告路径 |
| `agenttest/graph/build.py` | 流程图定义。哪五个节点、怎么连、哪条是回边 |
| `agenttest/graph/nodes.py` | 五个节点的实现。**全项目最核心、最长的文件（533 行）** |
| `agenttest/brain/mock_brain.py` | 不需要网络的「规则版大脑」，28 条用例写死在这里 |
| `agenttest/models.py` | 数据模型。用例长什么样、结果长什么样、缺陷长什么样 |
| `agenttest/tools/api_tool.py` | 最基础的「发一个 HTTP 请求」工具 |

### 1.3 跑第二次（用真实大模型）

先在 `.env` 里填上（参考 `.env.example`）：

```dotenv
AGENTTEST_LLM_API_KEY=sk-xxxx
AGENTTEST_LLM_BASE_URL=https://api.deepseek.com/v1
AGENTTEST_LLM_MODEL=deepseek-chat
```

再跑同样的命令。这次大脑换成了 `llm`：

```text
[runner] Brain = llm（LLM: deepseek-chat）
  [planner] llm 生成 23 条测试用例（--no-ui 过滤后 21 条）
  [executor] PASS API-008 创建待办后按返回 id 查询（写路径成对验证） (期望 201 / 实际 201 / 13ms)
  [executor] FAIL API-009 创建待办缺少 title 返回 400 (期望 400 / 实际 200 {'warning': 'created with empty title'} / 15ms)
  [critic] 失败 6/21，归因出 3 个缺陷
```

**对比这两次输出，你能立刻看出这个项目最有意思的地方**：
用例数量、用例标题、缺陷标题都不一样，但流程一模一样。
也就是说：**「想什么」可以换（Mock 换 LLM），「怎么干」完全不变**。
这是整个架构最重要的设计（第 9 章详讲）。

### 1.4 打开报告

用浏览器打开 `reports/report.html`，从上到下有四块：

| 区域 | 内容 | 读它的意义 |
| --- | --- | --- |
| 顶部深蓝条 | 目标 / Brain 名 / 被测地址 / 起止时间 | **证据**：证明这一轮用的是 Mock 还是真 LLM |
| 四张数字卡 | 用例总数 / 通过 / 失败 / 缺陷数 | 一眼看结论 |
| 🐞 缺陷列表 | 每条缺陷带 `severity/category` 标签 + 证据 + 建议 | 这是「结论」，人真正要看的部分 |
| 📋 用例明细表 | 每条的期望值 vs 实际值 vs 耗时 | 这是「过程」，用来复核结论 |
| 🗺️ 覆盖率 | 每个端点被哪几条用例覆盖 | 一眼看漏测了哪些接口 |
| 🧠 trace | 黑底等宽字体的完整思考轨迹 | 出问题时排查的第一现场 |

### 1.5 现在你已经知道的三件事

1. 它读契约（`已获取契约: ... 11 个端点`）→ 所以它不靠硬编码的接口清单。
2. 它按 `planner → executor → critic → reporter` 顺序干活 → 所以有「流程」。
3. 它会重试（`重试2次`）、会补跑（`第 1 轮补跑`）→ 所以不只会跑一次。

## 第 2 章 一张地图：每个文件是干什么的

### 2.1 先看整体目录

```
agent-test-hub/
├─ agenttest/          ← ★ Agent 本体（要被「读」的代码，3167 行）
│  ├─ brain/           ← 大脑：决定测什么、怎么归因
│  ├─ graph/           ← 流程图：五个节点 + 状态定义
│  ├─ tools/           ← 手脚：发请求、开浏览器、查检索
│  ├─ report/          ← 报告：HTML 渲染
│  ├─ models.py        ← 数据模型（全项目地基）
│  ├─ config.py        ← 配置

├─ demo_app/           ← 被测系统（故意有 bug 的靶子，≈2200 行）
```

> 读代码时**先不要读 tests/**，等你理解了主干再回头看，见第 12 章。

## 第 3 章 一次运行的完整生命周期（12 步）

这一章是全篇最重要的一章。我们把 `python -m agenttest run` 这一条命令，
像慢动作一样拆成 12 步，每一步都标出**在哪个文件的哪一行**。

### 3.0 全景时序图

```text
你敲下命令
   │
   ▼
[1] __main__.py ──────────────► runner.main()
   │
```

### 3.2 第 2 步：先把输出编码掰正

```python
# agenttest/runner.py:147-155
for stream in (sys.stdout, sys.stderr):
    reconfigure = getattr(stream, "reconfigure", None)
    if reconfigure is None:
        continue
    try:
        reconfigure(encoding="utf-8")
    except Exception:
        pass
```

**为什么**：Windows 控制台默认是 GBK 编码，而输出里有 emoji（🤖）和大量中文，
在某些终端下会直接抛 `UnicodeEncodeError` 让程序崩掉。
这里「尽力而为」：`getattr` 拿不到就跳过（老 Python 或特殊流），`try/except` 兜住。

**注意这个写法**：`getattr(stream, "reconfigure", None)` 而不是 `stream.reconfigure()`。
这是「鸭子类型」的防御性写法 —— 万一某个流对象没这个方法，不至于崩。
初学阶段可以理解为「不确定有没有，就先用 getattr 探一下」。

`Config.from_env()` 的实现在 `agenttest/config.py:166`。它的核心是这么一个小函数：

```python
def pick(name: str, default: str = "") -> str:
    """环境变量 > 档案文件 > 代码默认值。"""
    if name in os.environ:
        return os.environ[name].strip()
    if name in profile:
        return profile[name]
    return default
```

于是取值的优先级是：

| 优先级 | 来源 | 例子 |
| --- | --- | --- |
| 1（最高） | 真实环境变量（含 `.env` 文件注入的） | `export AGENTTEST_LLM_MODEL=gpt-4o-mini` |
| 2 | 档案文件 `scripts/env/<env>.env` | `staging.env` 里写 `AGENTTEST_DEMO_URL=http://127.0.0.1:5002` |
| 3（最低） | 代码里的默认值 | `llm_model: str = "deepseek-chat"` |

**为什么要有第二层「档案文件」？** 因为「本机开发」「预发环境」「生产」三套配置如果

第 10 章会把这个机制讲透，现在你只要记住：**配置项永远有三个可能来源，优先级从高到低。**

| --- | --- | --- | --- |

**第三个分支为什么必须单独处理**（这段代码的注释写得很直白，值得读一遍

> 远端目标没有 `/api/health`，也绝不该由我们来起。
> 把它硬塞进同一条流程，结果会是「远端目标被当成起不来的本机服务，
> 于是在原地起了一个本地 demo，测的还是自己」——这是最糟的一种假执行：
> 流程跑通、报告很绿、被测对象却不是你以为的那个。

这句话是软件工程里的一个重要概念：**「假执行比不执行更危险」**。
报告全绿但测错了对象，比直接报错更糟，因为你会相信它。

**`DemoServer` 是怎么起服务的？**

```python
# agenttest/runner.py:30-56
class DemoServer:
    def __init__(self, url: str) -> None:
        from demo_app.app import create_app          # ← 注意：函数内 import
        self.url = url.rstrip("/")
        raw_port = self.url.rsplit(":", 1)[-1]
        try:
            port = int(raw_port)
        except ValueError:
            raise ValueError(
                f"--demo-url 需要带端口的完整地址，例如 http://127.0.0.1:5001"
                f"（收到 {url!r}，解析出的端口部分是 {raw_port!r}）"
            ) from None
        self._server = make_server("127.0.0.1", port, create_app(), threaded=True)
        self._thread = threading.Thread(target=self._server.serve_forever, daemon=True)

    def start(self) -> None: self._thread.start()
    def stop(self) -> None:
        self._server.shutdown()
        self._thread.join(timeout=5)
```

三个关键点：

1. **`from demo_app.app import create_app` 写在函数内部**（不是文件顶部）。
   这叫「惰性导入 / 延迟导入」。好处是：如果我这次测的是远端 Petstore，
   根本不需要 `demo_app` 这个包（没装 Flask 也能跑）。
   只有真要起本地服务时才导入它。
2. **`make_server(..., threaded=True)`** 来自 `werkzeug.serving`，
   它比 `app.run()` 好的地方是：**不阻塞**，返回一个 server 对象，
   你自己决定在哪个线程跑。`app.run()` 会一直占着主线程不让走。
3. **`daemon=True`**：守护线程。主进程退出时它自动被杀，不会挂住不退出。
   （但如果主进程正常结束，还是应该在 `finally` 里显式 `stop()`，见第 12 步。）

**`wait_for_health` 为什么不用普通的 `requests.get`？**

```python
# agenttest/runner.py:59-75
def _direct_get(url: str, timeout: float) -> requests.Response:
    with requests.Session() as session:
        session.trust_env = False          # ← 关键这一行
        return session.get(url, timeout=timeout)

def wait_for_health(url: str, timeout: float = 30.0) -> bool:
    start = time.time()
    while time.time() - start < timeout:
        try:
            resp = _direct_get(f"{url}/api/health", timeout=2)
            if resp.status_code == 200:
                return True
        except requests.RequestException:
            pass
        time.sleep(0.3)
    return False
```

`session.trust_env = False` 的意思是「**不要读 `HTTP_PROXY` / `HTTPS_PROXY` 这些环境变量**」。

为什么这么重要？注释里写得很清楚（`agenttest/runner.py:60-65`）：

> 默认的 `requests` 会读 `HTTP_PROXY`，把发往 `127.0.0.1` 的探测交给代理。
> 代理回自己的 502 时，「服务还没起来」就永远判不出来 —— 轮询到超时后报"服务起不来"，
> 而真正挡住它的是代理。**就绪探测的可信度决定后面所有结论的可信度。**

这就是「环境无感」原则（第 10 章整章讲）。这里你只要理解：
**当你的测试工具本身被环境变量影响，那它给出的所有结论都只在这个 shell 里成立。**

另外注意 `wait_for_health` 是**轮询**（polling）：每 0.3 秒问一次，
最多问 30 秒。因为 Flask 启动需要时间（几十到几百毫秒），
不可能「起完立刻就能访问」。这是启动服务的标准做法。

```python
def fetch_openapi(base_url="http://127.0.0.1:5001", timeout=10.0, spec_url="", proxy=""):
    url = spec_url or f"{base_url.rstrip('/')}/openapi.json"
    with requests.Session() as session:
```

`build_graph` 在 `agenttest/graph/build.py:79-103`，全文如下（很短，但信息密度极高）：

```python
def build_graph(brain: BaseBrain, cfg: Config):
    graph = StateGraph(AgentState)
    graph.add_node("planner",  make_planner(brain, cfg))
    graph.add_node("executor", make_executor(cfg))
    graph.add_node("retrier",  make_retrier())
    graph.add_node("critic",   make_critic(brain))
    graph.add_node("reporter", make_reporter(brain, cfg))
    graph.set_entry_point("planner")
    graph.add_edge("planner", "executor")
    graph.add_conditional_edges(
        "executor",
        _route_after_executor(cfg),
        {"retrier": "retrier", "critic": "critic"},
    )
    graph.add_edge("retrier", "executor")
    graph.add_edge("critic", "reporter")
    graph.add_edge("reporter", END)
    return graph.compile()
```

逐句翻译成大白话：

| 代码 | 意思 |
| --- | --- |
| `StateGraph(AgentState)` | 建一张图，图里流动的「数据形状」是 `AgentState` |
| `add_node("planner", make_planner(brain, cfg))` | 注册一个叫 `planner` 的工位，工人是 `make_planner` 返回的函数 |
| `set_entry_point("planner")` | 从 `planner` 开始干 |
| `add_edge("planner", "executor")` | `planner` 干完自动去 `executor` |
| `add_conditional_edges(...)` | `executor` 干完后**要看情况**决定去哪（这是唯一的岔路） |
| `add_edge("retrier", "executor")` | `retrier` 干完回到 `executor`（这是唯一的回边） |
| `add_edge("reporter", END)` | `reporter` 干完就结束 |
| `graph.compile()` | 把图「编译」成可执行对象（LangGraph 会做校验和优化） |

**编译后得到的 `graph` 对象怎么用？** 就两行（下一步）：

```python
for step in graph.stream(state, stream_mode="updates"):
    ...
```

`stream` 的意思是「**流式**执行」：每执行完一个节点就吐一次结果，
而不是等五个节点全跑完才一次性返回。
`stream_mode="updates"` 表示「每次只吐这个节点**新增**的那部分 state」（增量），
而不是整份 state 快照。

**为什么用 stream 而不是 `invoke`？** 因为要「边跑边打印 trace」。
如果你用 `graph.invoke(state)`，用户会盯着屏幕几十秒什么都看不到，
最后才哗一下全部输出。流式让过程可见 —— 这也是「可观测性」的一部分。

注意 `executor` 被吐了**两次** —— 这就是回边（retrier → executor）在真实运行中的样子。

**箭头永远只朝下**（上层 import 下层，下层不 import 上层）。
这就是「分层架构」。它的好处：

1. **改上层不影响下层**：改 `runner.py` 不可能弄坏 `api_tool`。
2. **下层可单独测试**：`rag_metrics.py` 一个 import 内部都没有，
   所以 `tests/test_rag_engine.py` 能直接跑纯函数测试，不用起服务、不用联网。
3. **不会有循环 import**：Python 里 A import B、B import A 会直接报错，
   分层且只朝下就是从结构上杜绝这件事。

### 4.3 为什么 `models.py` 是地基（这一点很关键）

> 如果你想理解这个项目「数据是怎么流动的」，`models.py` 是你必须先读的文件。
> 只要看懂那 5 个类，剩下的代码基本就是「在生产/消费这 5 个类的实例」。

### 4.4 五种类的数据流

```text
Brain.make_plan()  ──生产──►  TestCase（用例）
                                  │
                                  ▼ executor 执行
                              TestResult（结果）
                                  │
                                  ▼ critic 归因
                                Defect（缺陷）
                                  │
                                  ▼ reporter 汇总
                              TestReport（报告）
                                  │
                                  ▼ 落盘
                       reports/report.json / report.html
```

**这是一条单向流水线。** 数据只会往下走，不会倒回去。
`TestResult` 里为什么会冗余存 `case_id`/`title`/`kind`？
因为报告只需要 `TestResult` 就能独立展示，不必再去 `cases` 里查 ——
这是「**结果自包含**」的设计，代价是一点点冗余，收益是报告层解耦。

### 4.5 `demo_app` 和 `agenttest` 的关系：它们**不该**有关系

```text
agenttest/  ──HTTP 请求──────────────────►  demo_app/
    │                                          （跑在另一个线程/进程/服务器上）
    │
    └─ 唯一的「代码级依赖」：runner.py 里那句惰性 import
       `from demo_app.app import create_app`（只在要起本地服务时才执行）
```

**这是这个项目最重要的架构选择**：Agent 不「import 被测系统」，而是「**通过 HTTP 访问**」它。

| | 如果是 import | 实际是 HTTP |
| --- | --- | --- |
| 能测远程系统吗 | ❌ 不能 | ✅ 能（Petstore 就是证据） |
| 能测别的语言写的服务吗 | ❌ 不能 | ✅ 能（只认 HTTP 和 JSON） |
| 能发现真实的序列化/网络问题吗 | ❌ 发现不了 | ✅ 能 |

**这就是为什么 `tools/api_tool.py` 用 `requests` 而不是 `store.list()`。**
一旦你在测试代码里 `import` 被测代码，测试和被测对象就绑死了，
那不叫「测系统」，那叫「测函数」。

### 4.6 如果我要新增一个「工具」，需要动哪些文件？

这是检验你有没有真懂依赖图的最好方法。假设你要加一个「查数据库」的工具：

| 步骤 | 改哪个文件 | 为什么 |
| --- | --- | --- |
| 1 | 新建 `agenttest/tools/db_tool.py` | 工具层，只能 import `models` / `config` / 标准库 |
| 2 | `agenttest/tools/__init__.py` 加一行 re-export | 保持「上层一行 import 拿到全部」的约定 |
| 3 | 如果要用在节点里，`graph/nodes.py` 里 import 它 | 只有节点才会"用"工具 |
| 4 | 写测试 `tests/test_db_tool.py` | 工具层要能被独立测试 |

**你完全不需要动** `models.py`、`config.py`、`brain/`、`report/` —— 除非新工具要产生新的数据类型。

| --- | --- | --- |

如果探针文档用中文，那么当分词器有 bug 时，探针本身就搜不出来，

### 6.0 五个节点的「统一约定」

在读任何节点之前，先记住这条铁律：

```python
def make_xxx(...):                        # 外层：接收依赖（brain / cfg）
    def xxx(state: Dict[str, Any]) -> Dict[str, Any]:   # 内层：只接收 state
        # 从 state 里读需要的
        # ... 干活 ...
        # 只 return 自己新增/修改的那几格
        return {"cases": ..., "trace": [...]}
    return xxx
```

对应到代码里的五个位置：

| 节点 | 工厂函数 | 返回什么 | 通俗职责 |
| --- | --- | --- | --- |
| planner | `nodes.py:33` | `{"cases": [...], "trace": [...]}` | 想：要测哪些点 |
| executor | `nodes.py:53` | `{"results": [...], "trace": [...]}` | 干：一条条执行 |
| retrier | `build.py:49` | `{"trace": [...]}` | 调度：还有能重试的吗 |
| critic | `nodes.py:477` | `{"defects": [...], "coverage": {...}, "trace": [...]}` | 判：哪里坏了 |
| reporter | `nodes.py:498` | `{"report": {...}, "trace": [...]}` | 说：写成报告 |

**注意 `trace` 每一个节点都返回。** 它用 `Annotated[List[str], add]` 声明了

### 6.1 planner：决定测什么

```python
# agenttest/graph/nodes.py:33-50（逐行讲解）
def make_planner(brain: BaseBrain, cfg: Config):
    def planner(state: Dict[str, Any]) -> Dict[str, Any]:
        cases = brain.make_plan(state["goal"], state["spec"], state["context"])
        #        └─ 把三样东西交给大脑：目标、契约、环境
        #           具体怎么生成，planner 完全不管 —— 这是「分层」

        reason = getattr(brain, "last_fallback_reason", "")
        #        └─ 用 getattr 而不是 brain.last_fallback_reason
        #           MockBrain 没有这个属性！getattr 带默认值才不会崩

        if reason:
            state["context"]["brain_fallback_reason"] = reason
            #  └─ 写进 context，一路传到报告，最后在 HTML 顶部打黄色警告条

        if state["context"].get("skip_ui"):
            kept = [c for c in cases if c.kind != "ui"]
            trace = [f"[planner] {brain.name} 生成 {len(cases)} 条测试用例（--no-ui 过滤后 {len(kept)} 条）"]
            if reason:
                trace.insert(0, f"[planner] LLM 规划失败，已降级规则引擎：{reason}")
            return {"cases": kept, "trace": trace}

        trace = [f"[planner] {brain.name} 生成 {len(cases)} 条测试用例"]
        if reason:
            trace.insert(0, f"[planner] LLM 规划失败，已降级规则引擎：{reason}")
        return {"cases": cases, "trace": trace}

    return planner
```

#### 为什么 planner 这么短？

因为**「怎么想」被完全外包给了 `brain`**。planner 只做三件事：
调大脑、过滤 UI、写 trace。这 18 行代码里没有任何一行在「设计测试用例」。

这就是「**决策与执行分离**」：planner 是执行骨架，brain 是决策逻辑。
换 brain 就等于换了整个「想」的能力，而 planner 一行都不用改。

#### 两个值得注意的技巧

**技巧 1：`getattr(brain, "last_fallback_reason", "")`**

`MockBrain` 里**没有** `last_fallback_reason` 这个属性（它不需要，因为它不调 LLM）。
如果直接写 `brain.last_fallback_reason` 就会 `AttributeError`。
`getattr(obj, "名字", 默认值)` 的意思是「有就取，没有就给默认值」。

但这里还有一层意思：这个属性只有 `LLMBrain` 在**降级时**才会设置
（`llm_brain.py:223`：`self.last_fallback_reason = ""` 初始为空）。
所以 `reason` 非空 ⟺ **这一轮本该用 LLM，但实际用了规则引擎**。
报告顶部那条黄色警告就是靠它触发的 —— 防止「把规则引擎的输出标成真实 LLM」。

**技巧 2：`trace.insert(0, ...)` 而不是 `trace.append(...)`**

降级原因要显示在**第一行**（因为它是解释后面所有内容的前提）。
`insert(0, x)` 把元素塞到最前面，`append(x)` 是塞到最后面。

#### 真实输出长什么样

| 情况 | trace 内容 |
| --- | --- |
| MockBrain，带 UI | `[planner] mock 生成 28 条测试用例` |
| MockBrain，`--no-ui` | `[planner] mock 生成 28 条测试用例（--no-ui 过滤后 25 条）` |
| LLMBrain 成功 | `[planner] llm 生成 23 条测试用例（--no-ui 过滤后 21 条）` |
| LLMBrain 降级 | `[planner] LLM 规划失败，已降级规则引擎：LLM 调用失败（APITimeoutError: ...）` + 下一行 `[planner] mock 生成 28 条...` |

分成四段来读：

#### 第 1 段：判断这一轮是「首轮」还是「补跑」（`nodes.py:67-73`）

```python

    trace_prefix = f"[executor] 补跑 {len(cases)} 条可重试用例（不重跑全量）"
```

**这段为什么重要？** 因为 executor 会被执行两次（首轮 + 补跑）。
如果没有这段判断，第二次执行会把**全部 25 条用例再跑一遍**：

- 白等两倍时间；
- 已经通过的用例再赌一次，万一这次 flaky 了反而变成失败 —— 把通过变成失败，纯亏。

代码注释写得很直接（`nodes.py:63-66`）：

> 不区分这两种情况，回边就退化成「全量重跑」，既有额外耗时又会把已经通过的用例再赌一次。

#### 第 2 段：单条用例的重试循环（`nodes.py:75-91`）

```python
for case in cases:
    start = time.perf_counter()
    attempts = 0
    last_detail = {"ok": False, "actual": "无响应", "error": "未执行"}
    retried = False
    while True:
        attempts += 1
        if case.kind == "api":
            last_detail = _run_api_case(case, base_url, base_proxy)
        elif case.kind == "rag":
            last_detail = _run_rag_case(case, base_url)
        else:
            last_detail = _run_ui_case(case, base_url, report_dir, cfg)

        if last_detail["ok"] or attempts >= cfg.max_attempts or not _retryable(_status_of(last_detail)):
            break
        retried = True
        time.sleep(0.3 * 2 ** (attempts - 1))   # 0.3s → 0.6s → 1.2s → …
```

**这是全项目最值得逐字读的 10 行代码。** 拆开看：

1. **`if/elif/else` 按 `case.kind` 分派** —— 这就是「一条用例三种跑法」的分岔点。
   `api` → `_run_api_case`，`rag` → `_run_rag_case`，剩下的（`ui`）→ `_run_ui_case`。
2. **`while True` + 三个 break 条件**，是重试逻辑的标准写法：

   | break 条件 | 含义 |
   | --- | --- |
   | `last_detail["ok"]` | 通过了，不用再试 |
   | `attempts >= cfg.max_attempts` | 试够 3 次了，认输 |
   | `not _retryable(status)` | **失败原因不值得重试** |

3. **`_retryable` 的判据**（`nodes.py:29-30`）：

   ```python
   def _retryable(status: int) -> bool:
       return status in (0, 500, 502, 503, 504)
   ```

   | status | 值得重试？ | 为什么 |
   | --- | --- | --- |
   | `0` | ✅ | 压根没拿到响应（连不上/超时）——可能是服务刚起来还没就绪 |
   | `500/502/503/504` | ✅ | 服务端自己的问题，可能是暂时的 |
   | `400/401/403/404` | ❌ | **业务 4xx 是确定性行为**，重跑一百遍还是 4xx |
   | `200`（但断言失败） | ❌ | 服务答了，只是答得不对 —— 重试也是同样答案 |

   **这条设计原则叫「失败分级」**：重试用来治「暂时性失败」，
   归因用来治「本质性失败」。混在一起会制造两种灾难：
   把真 bug 用重试掩盖掉，或把网络抖动报成缺陷。

4. **`0.3 * 2 ** (attempts - 1)` = 指数退避**：
   第 1 次失败睡 0.3s，第 2 次 0.6s，第 3 次 1.2s。
   为什么不用固定间隔？因为「服务刚重启」这种场景，等得越久恢复概率越大；
   同时指数退避能避免多个客户端同时打同一个刚挂的服务（惊群效应）。

#### 第 3 段：把结果包成 TestResult（`nodes.py:92-118`）

```python
# nodes.py:136-140  安全地从 dict 里取 int（取不到或取到脏值都返回 0）

# nodes.py:143-149  把「期望什么」变成人能读的一句话
def _expected_of(case):
    if case.kind == "api":
        return str(case.expected_status)                 # "400"
    if case.kind == "rag":

        return f"HTTP {case.expected_status}；{labels}" if labels else f"HTTP {case.expected_status}"
```

```python

    merged = {r.case_id: r for r in state["results"]}
    for r in results:
        merged[r.case_id] = r
    ordered = [merged[c.id] for c in state["cases"] if c.id in merged]
    # 消费掉补跑清单：不清空的话条件边会认为「还有失败待补跑」，
    # 在 retry_rounds 用完之前原地打转。
    ctx.pop("retry_case_ids", None)
    return {"results": ordered, "trace": trace}

```

逐句翻译：

| 行 | 干了什么 | 为什么必须这么干 |
| --- | --- | --- |
| `merged = {r.case_id: r for r in state["results"]}` | 把旧结果变「字典：id → 结果」 | 方便按 id 覆盖 |
| `merged[r.case_id] = r` | 用新结果覆盖同 id 的旧结果 | 补跑的结果比旧结果新 |
| `ordered = [merged[c.id] for c in state["cases"] if c.id in merged]` | 按 `cases` 的顺序重排 | **保持报告里的用例顺序不变**，否则补跑的那条会跑到表格最后一行，看着像新用例 |
| `ctx.pop("retry_case_ids", None)` | **清空**补跑清单 | 见下面 |

**`ctx.pop` 这一行是「状态机不卡死」的关键。** 想一下如果不清空会怎样：

```text
retrier 设置 ctx["retry_case_ids"] = ["API-006"]
  ↓
executor 补跑 API-006，返回 results（含 API-006 仍未通过）
  ↓
条件边 _route_after_executor 检查：_retry_candidates(results) 还能找到 API-006
  ↓
但它先检查 used >= cfg.retry_rounds（used=1, retry_rounds=1）→ 已经用完，去 critic
```

这个例子里恰好没卡住，因为轮次用完了。但如果 `retry_rounds` 配成 3，
不清空就会一直认为「还有失败待补跑」，白跑 2 轮。代码注释说的「原地打转」就是这个意思。

**「用完就清空」是状态机的通用纪律**：任何一次性信号（flag / 待办清单 / 锁）
用完必须显式复位，否则下次判断会读到过期的状态。

### 6.3 retrier 与条件边：唯一的一条「回边」

这两个概念放在一起讲，因为它们是一对：**条件边决定「去不去」，retrier 决定「去干什么」。**

#### 6.3.1 条件边（`agenttest/graph/build.py:64-76`）

```python
def _route_after_executor(cfg: Config):
    def route(state: Dict[str, Any]) -> str:
        ctx = state["context"]
        used = int(ctx.get("retry_round", 0))
        if used >= cfg.retry_rounds:
            return "critic"                      # 轮次用完 → 去归因
        if not _retry_candidates(state["results"]):
            return "critic"                      # 没有可重试的 → 去归因
        return "retrier"                         # 还有 → 去补跑

    return route
```

这段代码回答的问题只有一句：「**executor 干完了，接下来去哪？**」

三段判断，顺序不能换：

1. **先看轮次**：用完了就直接去 critic。哪怕还有 5xx 失败也不重试了。
   为什么要先判这个？因为 `retry_rounds` 是**硬上限**，
   它的存在就是为了防止「无限重试」把偶发 bug 永远掩盖下去。
2. **再看有没有可重试的**：没有就正常前进。
3. **都有才回退**。

返回值是字符串 `"retrier"` / `"critic"`，这个字符串被 `add_conditional_edges`
的第三个参数映射成实际节点名：

```python
graph.add_conditional_edges(
    "executor",
    _route_after_executor(cfg),               # ← 决策函数
    {"retrier": "retrier", "critic": "critic"},  # ← 返回值 → 节点名 的映射表
)
```

#### 6.3.2 「可重试的失败」到底怎么筛（`build.py:37-46`）

```python
RETRYABLE_STATUSES = (0, 500, 502, 503, 504)

def _retry_candidates(results: List[TestResult]) -> List[TestResult]:
    return [r for r in results
            if not r.ok                        # 失败的
            and not r.invalid_case             # 且不是「用例自己写错了」
            and r.actual_status in RETRYABLE_STATUSES]  # 且是 5xx/无响应
```

三个筛子，第三个尤其值得注意：

> `invalid_case=True` 的必须排除：那表示失败原因是**用例自己写错了**
> （例如把 RAG 断言写进 API 用例），补跑不会让它变绿，只会白烧一轮。

`invalid_case` 是 `TestResult` 上的一个字段（`agenttest/models.py:92-96`），
它的设计意图非常明确：

> 失败的原因是**用例本身写错了**，不是被测系统有问题。
> 归因时必须单独分类，否则「用例写错」会被报成缺陷。

**这是对一个非常隐蔽的错误的防御**：LLM 有时会在 API 用例里写
`Check(type="rag_recall_at_least")`（这是 RAG 专用断言）。
执行器看到不认识的断言类型 → 判失败 → 报告里出现一个「缺陷」→
但被测系统根本没问题，是 Agent 自己搞错了。
`invalid_case` 让这种情况能被单独归到 `test_issue` 类别。

#### 6.3.3 retrier 本体（`build.py:49-61`）

```python
def make_retrier():
    def retrier(state: Dict[str, Any]) -> Dict[str, Any]:
        ctx = state["context"]
        used = int(ctx.get("retry_round", 0)) + 1        # 轮次 +1
        ids = [r.case_id for r in _retry_candidates(state["results"])]
        ctx["retry_round"] = used
        # executor 读这个键：非空表示本轮只补跑这些用例，跑完清空。
        ctx["retry_case_ids"] = ids
        return {
            "trace": [f"[retrier] 第 {used} 轮补跑：{len(ids)} 条失败（5xx/无响应）可重试 {ids}；其余失败直接进归因"]
        }

    return retrier
```

retrier 短得惊人 —— **它根本不执行任何测试**。它只做三件事：

1. 把 `ctx["retry_round"]` 加 1（记账）；
2. 把「要补跑哪些 case_id」写进 `ctx["retry_case_ids"]`（下命令）；
3. 写一行 trace。

然后图的边 `add_edge("retrier", "executor")` 把它送回 executor，
executor 开头那段 `retry_ids = set(ctx.get("retry_case_ids") or [])` 就读到了。

**为什么这个信号要放在 `context` 而不是 state 顶层？**

这是个很微妙但很值得想的点。`state` 的字段是有「合并语义」的：
LangGraph 会把节点返回的 dict 合并进 state。如果 executor 返回 `{"retry_case_ids": []}`，
那就得小心「空列表是覆盖还是不动」。放在 `context`（一个普通 dict）里，
就是「原地修改一个对象的属性」，语义更直接：**这是一个命令通道，不是数据通道。**

#### 6.3.4 为什么要设计两层重试？

项目里有两套重试，初学者极容易搞混：

| 机制 | 在哪 | 触发 | 间隔 | 上限 | 治什么 |
| --- | --- | --- | --- | --- | --- |
| **内层重试** | `executor` 的 `while True`（`nodes.py:80`） | 单条用例失败且 status 是 0/5xx | 0.3 / 0.6 / 1.2 秒 | `cfg.max_attempts`（默认 3） | **同一次抖动窗口内**的连续失败 |
| **外层补跑** | `retrier` 回边（`build.py:49`） | 全部跑完后仍有 0/5xx 失败 | 无固定间隔（跑完剩下的用例自然耗时） | `cfg.retry_rounds`（默认 1） | **时间窗口拉开后**的偶发失败 |

`build.py:15-19` 的注释解释了为什么要两层：

> executor 内部的 `max_attempts` 重试是**同一次执行里的连续退避**（0.3s/0.6s/1.2s），
> 对「服务端偶发 503」这类问题常常在同一次抖动窗口里连续失败；
> 而跨轮补跑把时间窗口拉开了，`/api/flaky` 这种概率性失败才有机会在第二轮通过。

`/api/flaky` 是**10% 概率返回 503**（`demo_app/app.py:227`）。
算一下：只靠内层 3 次重试，全失败概率是 `0.1³ = 0.1%`；加上外层补跑一次
（再 3 次），全失败概率是 `0.1⁶ = 0.0001%`。这就是两层重试的实际意义。

> **面试常问**：为什么不用「重试 10 次」一次搞定？
> 因为连续 10 次都在毫秒级间隔内，对「服务正在重启（要 3 秒）」这类故障毫无用处；
> 而且真正的确定性缺陷会被重试掩盖，报告变绿但 bug 还在。

### 6.4 critic：把失败变成结论

```python
# agenttest/graph/nodes.py:477-495
def make_critic(brain: BaseBrain):
    def critic(state: Dict[str, Any]) -> Dict[str, Any]:
        results = state["results"]
        defects = brain.analyze_failures(results, state["context"])
        #        └─ 又是把「怎么判」外包给 brain

        reason = getattr(brain, "last_fallback_reason", "")
        if reason:
            state["context"]["brain_fallback_reason"] = reason

        coverage: Dict[str, List[str]] = {}
        for case in state["cases"]:
            for key in _coverage_keys(case):
                coverage.setdefault(key, []).append(case.id)
        #  └─ 建「端点 → 用例 id 列表」的反向索引（报告里那张覆盖率表）

        trace = [f"[critic] 失败 {sum(1 for r in results if not r.ok)}/{len(results)}，"
                 f"归因出 {len(defects)} 个缺陷"]
        if reason:
            trace.append(f"[critic] LLM 归因失败，已降级规则引擎：{reason}")
        for d in defects:
            trace.append(f"[critic]   {d.id} [{d.severity}/{d.category}] {d.title} @ {d.endpoint}")
        return {"defects": defects, "coverage": coverage, "trace": trace}

    return critic
```

#### 6.4.1 覆盖率是怎么算的（`nodes.py:461-474`）

```python
def _coverage_keys(case: TestCase) -> List[str]:
    if case.kind == "api":
        return [f"{case.method.upper()} {case.path}"]        # "GET /api/todos"
    if case.kind == "rag":
        if _uses_consistency_probe(case):
            return list(RAG_CONSISTENCY_ENDPOINTS)           # 5 个端点
        return list(RAG_SEARCH_ENDPOINTS)                    # 1 个端点
    return [f"UI {case.url}"]                                # "UI http://127.0.0.1:5001/login"
```

**为什么一条用例可能返回「多个」端点？** 看 `nodes.py:435-453` 的注释，
这段是项目里最好的「修 bug 记录」之一：

> 旧实现把 10 条 RAG 用例一律记成同一个 `"RAG GET /api/rag/search"`，
> 于是报告里 `/api/rag/index`、`/api/rag/reindex`、`POST /api/rag/docs`、
> `DELETE /api/rag/docs/{doc_id}` 全部显示成「没有任何用例覆盖」，
> 而实际打这些端点的正是索引一致性探针用例 RAG-006。

也就是说：**覆盖率算错了会导致「看起来漏测了，其实测了」**，
反过来也可能「看起来覆盖了，其实没测」。所以这里按「用例实际会打哪些端点」精确声明：

```python
RAG_SEARCH_ENDPOINTS: List[str] = [f"GET {SEARCH_PATH}"]
RAG_CONSISTENCY_ENDPOINTS: List[str] = [
    f"GET {INDEX_PATH}",                    # GET  /api/rag/index
    f"POST {DOCS_PATH}",                    # POST /api/rag/docs
    f"DELETE {DOCS_PATH}/{{doc_id}}",       # DELETE /api/rag/docs/{doc_id}
    f"GET {SEARCH_PATH}",                   # GET  /api/rag/search
    f"POST {REINDEX_PATH}",                 # POST /api/rag/reindex
]
```

注意这些常量是从 `rag_tool` 里 import 来的（`nodes.py:25`）：

```python
from agenttest.tools.rag_tool import DOCS_PATH, INDEX_PATH, REINDEX_PATH, SEARCH_PATH
```

**这是「单一数据源」原则**：路径字符串只在 `rag_tool.py:23-26` 定义一次，
覆盖率声明和实际请求都用它。如果哪天路径改了，覆盖率不会跟着写错。

还有一个「诚实声明」也值得读（`nodes.py:444-445`）：

> 已知局限：coverage 记录的是「声明这些用例会打哪些端点」，不是执行期实测；
> 若要让它变成执行事实，需要把端点带进 TestResult 再从 executor 汇总（本次未做）。

`tests/test_rag_coverage.py` 就是用真实调用记录来核对这个「声明」有没有脱节
（5 个测试）。**「把局限写进注释，并用测试钉住声明与实现的一致性」**，
这是很成熟的工程做法。

#### 6.4.2 `setdefault(...).append(...)` 这个惯用法

```python
coverage.setdefault(key, []).append(case.id)
```

等价于：

```python
if key not in coverage:
    coverage[key] = []
coverage[key].append(case.id)
```

`dict.setdefault(k, default)`：键不存在就设成 `default` 并返回它；
键存在就返回当前值。所以后面那个 `.append()` 永远有一个 list 可以追加。
这是「一行建多重索引」的标准写法，Python 里非常常见。

### 6.5 reporter：写报告

见第 5.5 节的调用链。这里补充三个设计细节：

#### 细节 1：summary 是「算」出来的，不是「收」上来的

```python
total  = len(report.cases)
passed = sum(1 for c in report.cases if c.ok)
report.summary = {"total": total, "passed": passed,
                  "failed": total - passed, "defects": len(report.defects)}
```

为什么不信任 `executor` 报上来的数字？因为**汇总数字最容易和明细对不上**。
从明细现算，就永远不可能出现「卡片写 25 条，表格里有 24 行」这种尴尬。
`sum(1 for c in ... if c.ok)` 是 Python 的「数一数有几个满足条件」惯用法，
等价于 `len([c for c in report.cases if c.ok])`，但不创建中间列表。

#### 细节 2：`report_dir.mkdir(parents=True, exist_ok=True)`

```python
report_dir.mkdir(parents=True, exist_ok=True)
```

- `parents=True`：父目录不存在也一起建（`reports/a/b` 会建两层）。
- `exist_ok=True`：已存在也不报错（默认会抛 `FileExistsError`）。

没有这两行，第一次跑或者换个新目录跑就直接崩。

#### 细节 3：模板里的 `shot_exists` 辅助函数

```python
# agenttest/report/html_report.py:142-145
def shot_exists(case_id: str) -> bool:
    return (report_dir / f"screenshot_{case_id}.png").exists()

template.globals["shot_exists"] = shot_exists
```

为什么不在 Python 里先算好「哪些用例有截图」再传进模板？
因为 Jinja2 的模板是**一次渲染**的，传进去的变量得先全部准备好。
用 `template.globals` 注入一个**函数**，模板里就能在循环里按需调用
（`html_report.py:111`）：

```jinja2
{% if c.kind == 'ui' and shot_exists(c.case_id) %}
<img class="shot" src="screenshot_{{ c.case_id }}.png" alt="截图">
{% endif %}
```

好处是模板逻辑保持简单（不用预处理一个 `has_screenshot` 字典），
代价是模板渲染时会做文件系统 IO。这是个小取舍。

### 6.6 五个节点的心智模型总结

把五个节点想成一条**工厂流水线**：

```text
   ┌──────────┐   ┌──────────┐   ┌─────────┐   ┌──────────┐   ┌──────────┐
   │ planner  │──►│ executor │──►│ retrier │──►│  critic  │──►│ reporter │
   │ 出图纸   │   │ 干加工   │   │ 补返工  │   │ 质检判定 │   │ 出报告   │
   └──────────┘   └──────────┘   └─────────┘   └──────────┘   └──────────┘
        │              │              │              │              │
     写 cases      写 results     写 context    写 defects      写 report
                                   (命令通道)    + coverage      (文件路径)
```

四个要点：

1. **每个节点的输出是「增量」，不是「全量」**。它只 return 自己负责的那几格。
2. **只有 `trace` 是累加的**（靠 `Annotated[List[str], add]`），其他都是覆盖。
3. **依赖通过工厂函数的参数注入**（`brain`、`cfg`），不通过全局变量。
4. **决策逻辑全在 brain 里，执行逻辑全在节点里**。节点里没有一行 if 在判断"这是不是 bug"。

## 第 7 章 七个必须懂的概念

这一章把项目里反复出现、但初学者最容易卡住的七个概念讲清楚。
每个概念都配「项目里哪一行用到了」。

### 7.1 Pydantic 的 `BaseModel`：会自我校验的数据类

#### 它解决什么问题

普通 Python 类的问题是：**字段写错了没人管。**

```python
class TestCase:
    def __init__(self, id, title, kind):
        self.id = id
        self.title = title
        self.kind = kind

c = TestCase("API-001", "健康检查", "api")
c.kind = "apii"        # 拼错了？没人报错，等到执行时才崩
c.expexted_status = 200 # 拼错了？静默多出一个属性，永远不生效
```

Pydantic 的 `BaseModel` 会在**创建对象的那一刻**做三件事：
① 校验类型；② 「字段名拼错」直接报错；③ 补默认值。

#### 项目里的写法

```python
# agenttest/models.py:45-70（节选）
class TestCase(BaseModel):
    __test__ = False                    # ← 防止 pytest 把它当测试类收集（见 7.1.3）

    id: str = Field(description="用例唯一编号")
    title: str
    kind: Literal["api", "ui", "rag"] = "api"
    priority: Priority = "P1"
    method: str = "GET"
    path: str = ""
    query: Dict[str, str] = Field(default_factory=dict)
    body: Optional[Dict[str, Any]] = None
    expected_status: int = 200
    url: str = ""
    checks: List[Check] = Field(default_factory=list)
    rag_query: str = ""
    top_k: int = 5
    rag_relevant: List[str] = Field(default_factory=list)
    source: str = "spec"
```

四种「类型标注」的用法：

| 写法 | 含义 | 例子 |
| --- | --- | --- |
| `id: str` | 必填的字符串 | 少了 `id` 直接报错 |
| `id: str = "默认值"` | 有默认值，可不填 | `kind: Literal[...] = "api"` |
| `Optional[Dict] = None` | 可以是 `None` | `body: Optional[Dict[str, Any]] = None` |
| `Literal["api","ui","rag"]` | **只能是这三个值之一** | `c.kind = "apii"` 立刻报错 |

`Literal` 是这里最有价值的东西。它把「kind 只能是三种之一」这条规则
**写进了类型系统**，而不是靠注释和人的自觉。

#### 7.1.1 `Field(default_factory=list)` 为什么不能写成 `= []`

```python
# ❌ 绝对不要这么写
checks: List[Check] = []

# ✅ 项目里的写法
checks: List[Check] = Field(default_factory=list)
```

这是 Python 里最经典的坑之一：**可变默认值**。

```python
def f(x, acc=[]):     # ❌ 这个 [] 只在定义时创建一次！
    acc.append(x)
    return acc

f(1)   # [1]
f(2)   # [1, 2]   ← 糟糕，上一次的结果还在
```

`default_factory=list` 的意思是「每次创建新对象时，调用 `list()` 生成一个新的空列表」。
所以每个 `TestCase` 都有自己独立的 `checks` 列表，互不干扰。

**判断标准**：默认值是 `int/str/None/bool`（不可变）→ 直接写；
是 `list/dict/set`（可变）→ 必须用 `default_factory`。

#### 7.1.2 `model_dump_json()` 省掉了多少事

```python
# agenttest/graph/nodes.py:526
json_path.write_text(report.model_dump_json(indent=2), encoding="utf-8")
```

一行就把整个嵌套对象（含 `List[TestResult]`、`List[Defect]`、`Dict[str, int]`）
变成格式化好的 JSON。手写的话要处理：嵌套模型递归、`Path` 转字符串、
`datetime` 转 ISO 格式、中文不转义……全都得自己来。

#### 7.1.3 为什么每个模型都有 `__test__ = False`

```python
class TestCase(BaseModel):
    __test__ = False   # 避免被 pytest 当作测试类收集
```

pytest 收集测试的规则是：**文件名以 `test_` 开头 或 类名以 `Test` 开头**。
`TestCase`、`TestResult`、`TestReport` 全都以 `Test` 开头 —— pytest 会试图
实例化它们并抱怨「没有 test_ 开头的方法」。

`__test__ = False` 是 pytest 官方的「别收我」标记。

> 这个坑几乎每个「写测试框架的项目」都会踩一次。看到 `__test__ = False`
> 就知道作者被咬过。

### 7.2 `TypedDict` + `Annotated[..., add]`：LangGraph 的状态

#### 7.2.1 为什么状态不用 Pydantic 类而用 TypedDict

```python
# agenttest/graph/state.py:11-21
class AgentState(TypedDict):
    goal: str
    spec: Dict[str, Any]
    cases: List[TestCase]
    results: List[TestResult]
    defects: List[Defect]
    coverage: Dict[str, List[str]]
    trace: Annotated[List[str], add]      # ← 唯一特殊的一个
    started_at: str
    context: Dict[str, Any]
    report: Dict[str, Any]
```

`TypedDict` 和 `BaseModel` 的区别是本质性的：

| | `BaseModel`（Pydantic） | `TypedDict`（typing） |
| --- | --- | --- |
| 运行时是什么 | 一个**对象**（有 `__dict__`） | 就是一个**普通 dict**！ |
| 会校验吗 | ✅ 创建时校验 | ❌ 纯标注，运行时零开销 |
| 能 `.model_dump_json()` 吗 | ✅ | ❌（但也用不着，dict 本来就能 json 化） |
| 为什么选它 | 数据要序列化/校验 | 状态每步都传递，要轻 |

LangGraph 的状态是**每走一个节点就合并一次**的，用普通 dict 最省。
`TypedDict` 只是给编辑器和 mypy 看的「形状说明」，运行时什么都不做。

#### 7.2.2 `Annotated[List[str], add]` 到底是什么

这是全项目最抽象的一行，必须讲清楚。

**默认行为**：节点返回 `{"cases": [...]}`，LangGraph 就**覆盖** state 里的 `cases`。
因为 `cases` 没有特殊标注。

**但 `trace` 不一样**：它标了 `Annotated[List[str], add]`。
`Annotated[T, x]` 的意思是「类型是 T，附带元信息 x」。这里 x 是 `operator.add`。
LangGraph 看到这个元信息，就会用 `add` 来**合并**新旧值：

```python
# 等价于这个意思
state["trace"] = state["trace"] + update["trace"]     # operator.add 对 list 就是拼接
```

所以：

```text
初始   trace = []
planner 返回 {"trace": ["[planner] …"]}          → trace = ["[planner] …"]
executor 返回 {"trace": ["[executor] PASS …", "…"]} → trace = ["[planner]…", "[executor]…", "…"]
critic 返回 {"trace": ["[critic] …"]}             → 又来一行
reporter 返回 {"trace": ["[reporter] …"]}         → 最后一行
```

**为什么只有 trace 需要 `add`？** 因为它是唯一一个「多方共同写入」的字段。
其他字段都只有一个节点负责：只有 planner 写 `cases`，只有 executor 写 `results`。
让它们覆盖，是简化，也是安全（不会出现「上一轮的结果混进这一轮」）。

> **一句话记住**：`Annotated[list, add]` = 「这个字段请追加，不要覆盖」。

#### 7.2.3 如果搞混会发生什么（类比）

想象你在白板上写字：

- `cases` 这类字段是「**擦掉重写**」—— planner 写完后，只有它自己会再改。
- `trace` 是「**接着往下写**」—— 五个人轮流来，谁都不能擦掉别人写的。

如果 `trace` 也用了覆盖，那报告里只会剩最后一行的 `[reporter] 报告已生成`，
前面所有过程全丢 —— 而 trace 的最大价值就是「事后能复盘每一步」。

### 7.3 `StateGraph` 的三件套：节点 / 边 / 状态

LangGraph 里只有三个概念，非常少：

| 概念 | 代码 | 类比 |
| --- | --- | --- |
| **节点（node）** | `graph.add_node("名字", 函数)` | 一个工位，函数就是一个工人 |
| **边（edge）** | `graph.add_edge("A", "B")` | 传送带，A 干完自动送到 B |
| **条件边（conditional edge）** | `graph.add_conditional_edges("A", 决策函数, 映射表)` | 岔路口，看决策函数的返回值决定去哪 |
| **状态（state）** | `StateGraph(AgentState)` | 跟着工件走的「工序卡」，每站都往上写 |

还有三个必须知道的：

| | 代码 | 说明 |
| --- | --- | --- |
| 入口 | `graph.set_entry_point("planner")` | 从哪开始 |
| 终点 | `add_edge("reporter", END)` | `END` 是 LangGraph 内置的哨兵值 |
| 编译 | `graph.compile()` | 得到可执行对象，之后只能 `invoke` / `stream` |

**为什么一定要 `compile()`？** 因为它做三件事：
① 校验所有边指向的节点都存在（写错节点名会在这里报错）；
② 检查有没有孤立节点；
③ 生成执行计划（决定哪个节点能并行跑）。

**这个项目的图有一个特点：它是「链」不是「扇出」。**
五个节点串成一条线，只有一处岔路（executor 之后）和一条回边（retrier → executor）。
没有并行。这不是能力不足，是刻意的：**并行执行测试会让失败原因难以归因**
（两条用例同时打同一个服务，拿到 503 你分不清是谁影响的谁）。

### 7.4 `Protocol`：只要长得像，就是

```python
# agenttest/brain/base.py:10-19
from typing import Protocol

class BaseBrain(Protocol):
    name: str

    def make_plan(self, goal: str, spec: Dict[str, Any], context: Dict[str, Any]) -> List[TestCase]:
        """根据目标与契约生成测试计划（用例列表）。"""
        ...

    def analyze_failures(self, results: List[TestResult], context: Dict[str, Any]) -> List[Defect]:
        """分析失败用例，产出缺陷结论。"""
        ...
```

#### `Protocol` 和「抽象基类（ABC）」的区别

| | ABC（`class X(ABC)`） | Protocol |
| --- | --- | --- |
| 怎么算「是」这个类型 | 必须**显式继承** `class MockBrain(BaseBrain)` | **只要方法签名对得上就是**（鸭子类型） |
| 能强制检查吗 | ✅ 继承时 | ✅ mypy 静态检查时 |
| 能实例化吗 | ❌ 必须实现所有抽象方法 | ✅ Protocol 本身能被当类型用 |

注意项目里 `MockBrain` 和 `LLMBrain` **都没有继承 `BaseBrain`**：

```python
# agenttest/brain/mock_brain.py:15
class MockBrain:                    # ← 没有 (BaseBrain)
    name = "mock"
    def make_plan(...): ...
    def analyze_failures(...): ...

# agenttest/brain/llm_brain.py:207
class LLMBrain:                     # ← 也没有
    name = "llm"
    def make_plan(...): ...
    def analyze_failures(...): ...
```

它们只是「长得像」，于是 mypy 就认为它们「是」`BaseBrain`。
这就是「结构化子类型 / 鸭子类型」：**不看你姓什么，看你会什么。**

#### 为什么要这么设计

`BaseBrain` 只出现在**类型标注**里（`make_planner(brain: BaseBrain, ...)`），
不是运行时强约束。好处：

1. **加第三个大脑零成本**：写个新类，实现两个方法，不用改任何继承关系。
2. **测试可以造极简假大脑**：写一个只有 `name` + 两个方法的小类就能替身，
   不需要继承、不需要注册。
3. **`LLMBrain` 不需要知道 `BaseBrain` 存在**，`brain/` 包内文件之间零耦合。

#### 接口只有两个方法 —— 这是刻意的

```python
make_plan(goal, spec, context)       → List[TestCase]    # 想：测什么
analyze_failures(results, context)   → List[Defect]      # 判：哪坏了
```

**整个「智能」被压缩成两个纯函数。** 这个约束非常强，好处是：

- 想换模型？只改这两个方法的实现。
- 想接别家 LLM？同上。
- 想加个「从 Jira 读用例」的大脑？同上。
- 想测试节点逻辑？传个假大脑，两个方法各返回固定值即可。

> **面试可以这么讲**：「Agent 的智能部分被约束成一个 2 方法的接口，
> 执行部分是完全确定性的代码。这样『概率性』和『确定性』在架构上就隔离开了。」

### 7.5 工厂函数 + 闭包 = 依赖注入

这个模式在第 6 章反复出现（五个节点全是），这里统一讲透。

#### 问题：LangGraph 只按「一个参数」调用节点

```python
# LangGraph 内部大致这么调
update = node_function(state)          # ← 只会传 state
```

但我们的节点需要 `brain` 和 `cfg`。怎么办？

#### 解法一（项目没用）：全局变量

```python
BRAIN = None                # ❌ 全局可变状态
CFG = None

def planner(state):
    return {"cases": BRAIN.make_plan(...)}
```

问题：测试时得改全局变量，跑完还得改回来；两个测试并行跑会互相干扰。

#### 解法二（项目用的）：闭包捕获

```python
def make_planner(brain, cfg):        # ① 建图时把依赖传进来
    def planner(state):              # ② 这个函数只接收 state
        return {"cases": brain.make_plan(...)}   # ③ brain 从闭包里"看见"
    return planner                    # ④ 返回这个绑好了依赖的函数
```

`brain` 是被内层函数「捕获」的。这叫**闭包（closure）**。
建图时：

```python
graph.add_node("planner", make_planner(brain, cfg))
#                            └─ 这里就把 brain 绑进去了
```

之后 LangGraph 无论怎么调 `planner(state)`，它都已经知道用哪个 brain 了。

#### 为什么这是「依赖注入」

因为**依赖是从外部传进来的，不是内部创建的**。对比：

```python
# ❌ 内部自己创建：无法替换
def make_planner():
    brain = LLMBrain(Config())     # 硬编码！测试时没法换成假的，也没法用 MockBrain
    ...

# ✅ 外部传入：可替换
def make_planner(brain, cfg):
    ...
```

`runner.py` 是唯一「决定用哪个 brain」的地方（第 3.7 步的 `pick_brain`），
其他所有文件都只接受「一个 brain」而不关心它是哪一种。
这就叫「**组合根（composition root）**」：所有依赖的选择集中在一个地方。

### 7.6 惰性导入：为什么有些 import 写在函数里

项目里有三处「函数内 import」，每一处都有明确理由：

| 位置 | 代码 | 理由 |
| --- | --- | --- |
| `runner.py:34` | `from demo_app.app import create_app` | 测远端系统时不需要 Flask/demo_app，导入了就白装 |
| `nodes.py:500` | `from agenttest.report.html_report import render_html_report` | 只有真写报告时才需要 jinja2 |
| `llm_brain.py:226` | `from langchain_openai import ChatOpenAI` | 不配 LLM 时不需要 langchain，MockBrain 可以零依赖运行 |
| `llm_brain.py:55` | `import httpx` | 同上 |
| `ui_tool.py:83` | `from selenium import webdriver` | 用 chrome 后端时完全不碰 selenium |
| `llm_brain.py:283` | `from agenttest.brain.mock_brain import MockBrain` | **避免循环导入**：mock_brain 也在 brain 包里 |

**前五个是「省依赖」，第六个是「破环」。** 第六个要特别说一下：

```python
# brain/__init__.py 里同时 import MockBrain 和 LLMBrain
from .mock_brain import MockBrain
from .llm_brain import LLMBrain
```

如果 `llm_brain.py` **顶部**写 `from agenttest.brain.mock_brain import MockBrain`，
那么导入顺序是：`brain/__init__` → `llm_brain` → `mock_brain` → 回到 `llm_brain`…
虽然 Python 能处理这个特定情况，但在更复杂的依赖里很容易变成
`ImportError: cannot import name 'X' from partially initialized module`。
把它挪进函数体里（真正用到时才导入）就彻底避开了。

**判断标准**：
- 顶部 import = 「这个模块离不开它」；
- 函数内 import = 「不一定用得上」或「会导致循环」。

代价：函数内 import 每次调用都要查一次 `sys.modules`，有微小开销
（Python 缓存了，实际可忽略）。所以别滥用 —— 项目里只有 6 处。

### 7.7 「未实现必须判失败」：一个反直觉但极重要的原则

这个原则在项目里出现了**四次**，每次注释都写得斩钉截铁。

#### 出现位置

```python
# 1. RAG 断言 —— nodes.py:355
return {"ok": False, "detail": f"未实现的断言类型 {check.type}（executor 未支持，按失败处理）"}

# 2. API 断言 —— nodes.py:221-226
return {"ok": False, "invalid": True,
        "detail": f"API 用例不支持的断言类型 {check.type}（该断言只对 RAG/UI 用例有效，属用例本身写错，不计为被测缺陷）"}

# 3. UI（chrome 后端）—— ui_tool.py:171-180
else:
    # 未实现的断言类型必须判失败：静默跳过会让 all([]) 组合出假绿
    results.append({"type": c.type, "target": c.target, "ok": False,
                    "detail": f"未实现的断言类型 {c.type}（UI 后端未支持，按失败处理）"})

# 4. UI（selenium 后端）—— ui_tool.py:110-119，同上一模一样
```

#### 为什么反直觉

大多数人的直觉是「不认识的类型就跳过吧，别让程序崩」。
但注释点破了要害：

> **静默跳过会让 `all([])` 组合出假绿。**

看这段代码（`ui_tool.py:185`）：

```python
return {"ok": all(r["ok"] for r in results), ...}
```

如果遇到不认识的断言就 `continue`（跳过），那么：

```text
用例 checks = [Check(type="某个我不认识的类型")]
  ↓ 跳过
results = []                          ← 空的！
ok = all([]) = True                   ← Python 里空集合的 all() 是 True！
```

结果：**一条什么都没验证的用例显示 PASS**。报告变绿，测试等于没写。

#### 更严重的一层：它会污染归因

`nodes.py:308-310` 的注释：

> 未实现的 check.type **必须判失败**：旧实现在末尾兜底返回 `ok=True`，
> 任何漏写分支的新断言类型都会静默通过（假绿），这比断言失败更危险。

「假绿」比「假红」危险得多：

| 现象 | 你会怎么做 | 后果 |
| --- | --- | --- |
| 假红（没实现就报错） | 立刻发现，去修 | 5 分钟修好 |
| 假绿（没实现就通过） | 什么都不知道 | 上线后炸，且你**以为已经测过了** |

#### 这条原则的通用形式

> **对于「我不知道该怎么判断」的情况，默认结论必须是「失败/不确定」，
> 而不是「通过」。**

项目里还有两处同样的精神：

```python
# rag_metrics.py:81-92 —— 没有标注相关文档时，recall 返回 0.0 而不是 1.0
def recall_at_k(hits, relevant, k):
    if not relevant:
        return 0.0     # 「没有标注就无从判断是否漏召，不能按『无可漏项』记满分」

# nodes.py:330-336 —— 阈值断言但没有标注时，判失败
if not case.rag_relevant:
    return {"ok": False,
            "detail": "用例没有标注相关文档（rag_relevant 为空），recall 无定义——"
                      "标注缺失按失败处理，不按「无可漏项」记满分"}
```

**两次都指向同一个陷阱**：数学上「空集的召回率」可以定义成 1（没漏任何东西），
工程上这么定义就是灾难 —— 一条什么都没标注的用例会永远通过。

## 第 8 章 三条执行路径：API / UI / RAG

`executor` 按 `case.kind` 分成三路。三路的技术栈完全不同，
这是这个项目「覆盖面广」的体现，也是初学者最容易迷路的地方。

```text
                        ┌──────────────────────────────┐
  case.kind == "api" ──►│ _run_api_case   → requests    │  HTTP 状态码 + 响应体断言
                        ├──────────────────────────────┤
  case.kind == "ui"  ──►│ _run_ui_case    → Chrome 无头 │  DOM 渲染 + CSS 选择器
                        ├──────────────────────────────┤
  case.kind == "rag" ──►│ _run_rag_case   → BM25 检索   │  召回质量 + 排序不变量
                        └──────────────────────────────┘
```

### 8.1 API 路径：最短也最基础

**调用链**：`executor` → `_run_api_case`（`nodes.py:167`）→ `api_request`（`api_tool.py:34`）

**双断言设计**（`nodes.py:169-206`）：

```python
def _run_api_case(case, base_url, proxy=""):
    detail = api_request(case.method, case.path, query=case.query, body=case.body,
                         headers=case.headers, base_url=base_url, proxy=proxy)
    actual = detail.get("status", 0)
    ok = bool(detail.get("ok")) and actual == case.expected_status
    failures = []
    invalid = False
    if not detail.get("ok"):
        failures.append(detail.get("error") or "请求失败")
    elif actual != case.expected_status:
        failures.append(f"期望状态码 {case.expected_status}，实际 {actual}")

    # 关键：状态码对了还要继续查响应体
    for check in case.checks:
        verdict = _eval_api_check(check, detail.get("body"))
        if not verdict["ok"]:
            failures.append(verdict["detail"])
            invalid = invalid or bool(verdict.get("invalid"))

    return {"ok": ok and not failures, "status": actual, ...}
```

注释直接点出为什么要有第二层断言（`nodes.py:170-174`）：

> 状态码不符即失败；`case.checks` 非空时还要逐条校验响应体关键字段
> （`contains_text` / `title_contains` / `has_element`），避免「**状态码对了就算过**」的假绿。

举例：`POST /api/todos` 返回 201，但响应体里 `data.title` 是 `"(empty)"` 而不是你传入的值。
只查状态码 → PASS；加了 `contains_text` 断言 → 能抓到。

**`_eval_api_check` 支持的三种断言**（`nodes.py:209-226`）：

| 断言类型 | 判据 | 典型用途 |
| --- | --- | --- |
| `contains_text` | 响应体 JSON 文本里包含 `target` 子串 | `target="token"` 验证登录返回了 token |
| `title_contains` | HTML `<title>` 里包含 `target` | 验证页面标题 |
| `has_element` | BeautifulSoup 能找到 CSS 选择器 `target` | 验证返回的 HTML 里有某个元素 |

**注意这三种对「JSON 响应」也适用** —— 因为 `_eval_api_check` 第一行就把 body 转成文本了：

```python
text = body if isinstance(body, str) else ("" if body is None else json.dumps(body, ensure_ascii=False))
```

### 8.2 UI 路径：不开驱动也能验证渲染

**这是项目里最巧的一块。** 传统 Selenium 要装 chromedriver、对版本、起浏览器进程，
麻烦且容易挂。项目提供了两条路：

| 后端 | 原理 | 需要什么 | 能力 |
| --- | --- | --- | --- |
| `chrome`（默认） | `chrome --headless=new --dump-dom <url>` 拿渲染后的 DOM | 系统装了 Chrome/Edge | 只读验证（文本/元素/标题）+ 截图 |
| `selenium` | Selenium WebDriver | chromedriver | 完整交互（填表/点击） |

#### chrome 后端的核心（`ui_tool.py:40-56`）

```python
def _chrome_dump_dom(chrome_path: str, url: str) -> str:
    cmd = [
        chrome_path,
        "--headless=new",          # 新版无头模式（渲染更接近真实浏览器）
        "--disable-gpu",
        "--no-sandbox",
        "--disable-dev-shm-usage",
        "--dump-dom",              # ← 关键：渲染完把 DOM 打到 stdout
        url,
    ]
    proc = _run_cmd(cmd)
    if proc.returncode != 0:
        raise UiUnavailableError(f"chrome dump-dom 失败: {proc.stderr[:500]}")
    if not proc.stdout:
        raise UiUnavailableError("chrome dump-dom 未返回内容")
    return proc.stdout
```

**`--dump-dom` 是本项目的「魔法开关」**：它让 Chrome 像一个普通命令行程序一样，
启动 → 加载 → 执行 JS → 渲染 → 把最终 DOM 打到标准输出 → 退出。
不需要 driver、不需要端口、不需要协议。拿到的 HTML 字符串交给 BeautifulSoup 做断言。

这个设计的价值：**CI 上只要能装 Chrome，UI 能力就能跑**。
而 GitHub 的 ubuntu runner 自带 Chrome（`/usr/bin/google-chrome`）。

#### 页面断言怎么做（`ui_tool.py:147-189`）

```python
dom = _chrome_dump_dom(found_chrome, url)
soup = BeautifulSoup(dom, "html.parser")
body_text = soup.get_text(" ", strip=True)        # ← 所有可见文本拼起来

for c in checks:
    if c.type == "contains_text":
        ok = c.target in body_text
    elif c.type == "has_element":
        ok = bool(soup.select_one(c.target))      # ← CSS 选择器
    elif c.type == "title_contains":
        title = soup.title.string if soup.title else ""
        ok = c.target in (title or "")
    else:
        ok = False                                # ← 未实现必须失败（7.7 节）
```

四个实现细节值得学：

1. **`soup.get_text(" ", strip=True)`**：把 HTML 里所有文本节点用空格拼起来并去首尾空白。
   直接对 HTML 字符串做 `in` 判断会误命中标签名/属性名
   （比如找 `"login"` 会命中 `<form action="/login">`，但页面上其实没显示这个词）。
2. **`soup.select_one(selector)`**：CSS 选择器（`.class`、`#id`、`[data-testid=x]`）。
   比 XPath 更简单，且浏览器和 BeautifulSoup 都支持同一套语法。
3. **`if soup.title else ""`**：`soup.title` 可能是 `None`（页面没 `<title>`）。
   不加判断会 `AttributeError: 'NoneType' object has no attribute 'string'`。
4. **`c.target in (title or "")`**：再兜一层，防止 `title.string` 是 `None`
   （`<title></title>` 空标题的情况）。

#### 截图为什么失败也不阻断（`ui_tool.py:59-79`）

```python
def _chrome_screenshot(chrome_path, url, out_path):
    try:
        abs_path = str(out_path.resolve())   # ← Chrome 对相对路径解析异常，必须绝对路径
        proc = _run_cmd([chrome_path, "--headless=new", ..., f"--screenshot={abs_path}", url])
        if proc.returncode == 0 and out_path.exists():
            return str(out_path)
    except Exception:
        pass                                  # ← 吞掉所有异常
    return None
```

**截图是「nice to have」不是「必须有」**：断言通过与否由 DOM 决定，
截图只是给人看的证据。截图失败就把测试判失败，属于把辅助功能当核心功能。
所以这里**故意**吞掉异常（`except Exception: pass`）并返回 `None`。

> 注意：这是项目里少见的「宽泛 except」。它合理，因为**截图失败的原因无法穷举**
> （路径太长、磁盘满、Chrome 版本差异、权限…），而且失败后果可控（少一张图）。

#### `UiUnavailableError`：环境问题要单独抛

```python
# ui_tool.py:24-25
class UiUnavailableError(RuntimeError):
    """UI 后端不可用（未找到浏览器或驱动）。"""
```

`_run_ui_case` 会单独捕获它（`nodes.py:424-432`）：

```python
except UiUnavailableError as exc:
    return {"ok": False, "status": 0, "actual": "UI 不可用", "error": str(exc),
            "notes": ["UI 后端不可用，该用例失败"]}
```

**为什么单独一个异常类？** 因为「环境没装浏览器」和「页面真的缺元素」
是两件完全不同的事。前者应归因到 `environment`，后者才是被测缺陷。
用独立异常类，上层才能区分（虽然是 Catch 后都判失败，但 `error` 文本不同，
归因时能分开）。

### 8.3 RAG 路径：检索质量怎么变成可断言的东西

这是三条路里最抽象的一条，但也是最能体现「测试思维」的一条。

#### 8.3.1 为什么 RAG 难测

传统接口是「输入 → 输出，对就是对」：

```text
GET /api/todos/1  → 200 {"id":1, "title":"..."}     ✅ 确定性
```

检索接口是「输入 → 一组结果 → **质量好不好**」：

```text
GET /api/rag/search?q=向量数据库  → 200 {"hits": [{doc_id: "DOC-CN-002", score: 0.83, rank: 1}, ...]}
```

状态码是 200，但**召回的文档完全不相干** —— 这算通过还是失败？
「相关性」本身没有绝对答案。所以必须把它**转化成一堆可判定的性质**。

#### 8.3.2 三种「可判定」的性质

项目的做法是把「检索质量」拆成三类可以用代码判断的东西：

| 类型 | 项目里的名字 | 例子 | 为什么可判定 |
| --- | --- | --- | --- |
| **不变量** | `rag_rank_monotonic`、`rag_tie_by_doc_id`、`rag_no_duplicate` | 「分数必须降序」 | 数学性质，永远成立 |
| **一致性** | `rag_no_ghost_hit` | 「删掉的文档不能再被搜到」 | 因果必然 |
| **指标阈值** | `rag_recall_at_least`、`rag_mrr_at_least` | 「recall@5 ≥ 0.8」 | 有标注集就能算 |

**这三类的共同点：都不需要人来看「相关性好不好」。** 这就是能把 RAG 纳入
自动化测试的关键 —— 把主观的「相关性」变成客观的「不变量 + 一致性 + 指标」。

#### 8.3.3 recall@k 和 MRR 到底是什么（`rag_metrics.py:81-116`）

```python
def recall_at_k(hits, relevant, k) -> float:
    """recall@k：标注相关文档中被 top-k 召回的比例。"""
    if not relevant:
        return 0.0
    expected = {str(doc_id) for doc_id in relevant}
    retrieved = set(doc_ids_of(hits)[: max(int(k), 0)])
    return len(retrieved & expected) / len(expected)
```

**用大白话解释 recall@k**：

> 我事先知道「搜 A 这个词，正确答案是 1 号、3 号两篇文档」。
> 你返回前 5 条里包含了 1 号，没包含 3 号 → `1 / 2 = 0.5`。

`len(retrieved & expected)` 里的 `&` 是**集合交集**：
「你返回的」∩「应该有的」= 你找对了几个。

**用大白话解释 MRR**：

> 我只关心「第一篇正确答案排在第几位」。
> 排第 1 → `1/1 = 1.0`；排第 3 → `1/3 ≈ 0.333`；压根没出现 → `0`。

```python
def reciprocal_rank(hits, relevant) -> float:
    expected = {str(doc_id) for doc_id in relevant}
    if not expected:
        return 0.0
    for position, hit in enumerate(hits or [], start=1):
        if str(hit.get("doc_id")) in expected:
            return 1.0 / position
    return 0.0
```

**MRR = 多个查询的 RR 的平均值。**

> **两个指标的区别一句话**：
> **recall 看「有没有漏」，MRR 看「排得够不够靠前」。**
> 一篇文档在第 5 名被召回，recall@5 满分，MRR 只有 0.2。

#### 8.3.4 一个非常深的设计点：不用被测系统自报的 `rank`

```python
# rag_metrics.py:95-110 的 docstring（这段值得逐字读）
"""RR：首个相关文档在**返回列表里的位次**的倒数；未召回相关文档时为 0.0。

位次取 `enumerate` 的下标，不取 hit 自报的 `rank` 字段。原因：`rank` 是被测
系统自己写进响应体的，用被测方自报的位次去评被测方的排序质量，等于让它自己
给自己打分 —— `BUG_RAG_SORT_ASC`（分数升序）与并列顺序缺陷恰好都污染这个字段，
此时 RR 会显示 1.0，把真实的排序缺陷盖过去。
位次是评测方观察到的事实，rank 字段只是被测方的一句话。
"""
```

这段话是整个项目里最精彩的一段推理。展开讲：

**`rank` 是「被测方写进响应体的一个数字」**（`demo_app/rag.py:356` 那一行就是在做这件事）：

```python
{"doc_id": doc_id, "score": round(float(score), 6), "rank": rank, "text": ...}
```

它和 `score`、`text` 一样，都是被测系统**自己说**的。而检索质量要评的恰恰是
「被测系统排得好不好」，那么用一个由它自己给出的位次去评它的排序，
逻辑上就是循环论证 —— **它说自己是第一，你就认它是第一**。

再看评测方能**独立观察到**的东西：`hits` 这个列表的**实际元素顺序**。
`enumerate(hits, start=1)` 拿到的位置，是响应体字节流的物理次序，
被测方无法通过「多写一个字段」来篡改它。

所以关键差别不在「两个数字此刻是否恰好相等」，而在**失败模式不同**：

| 评测器依据 | 被测方 bug 恰好让 `rank` 失真时 | 会发生什么 |
| --- | --- | --- |
| `hit["rank"]` | `rank` 与实际输出顺序脱钩（比如写死、或按分数重排后再编号） | 评测器读到「第一名」，**RR = 1.0 满分**，真实的排序缺陷被抹平 |
| `enumerate` 下标 | 无论 `rank` 字段怎么写 | 位置就是位置，缺陷照实暴露 |

**注意这两种失败模式的严重程度完全不对等**：用 `rank` 时不一定会出错
（多数情况下它和实际位置一致），但**一旦被测方在这个字段上有 bug，
评测器就会跟着它一起错，而且错成「满分」** —— 这是最坏的一种错：
缺陷被伪装成完美。用 `enumerate` 则根本不存在这条被污染的通路。

`BUG_RAG_SORT_ASC`（注释点名的那两个缺陷之一）把列表按分数升序重排，
`BUG_RAG_NO_TIEBREAK` 让并列项次序不稳定 —— **这两个缺陷都作用在「顺序」上，
而 `rank` 字段正是被测方对「顺序」的描述**。顺序被改坏时，
人对顺序的描述大概率也跟着坏掉，此时再拿这个描述去评判顺序，等于什么都没测。

> **通用原则**：**评测者只能相信自己能观察到的事实，不能相信被测者对自己的描述。**
> 这和「考试不能让学生自己批卷」是同一个道理。
> 项目里其它地方也有同样的精神：
> - `rag_no_ghost_hit` 用「语料快照 vs 检索结果」对比，不信被测系统说「已删除」
> - `index_size != corpus_size` 用两个独立接口的数字交叉验证

#### 8.3.5 三个不变量的实现（`rag_metrics.py:154-190`）

```python
def check_rank_monotonic(hits):
    """rank 必须为 1..n 连续，score 必须单调非增。"""
    items = list(hits or [])
    ranks = [int(hit.get("rank") or 0) for hit in items]
    if ranks != list(range(1, len(items) + 1)):
        return {"ok": False, "detail": f"rank 不连续: {ranks}"}
    for index in range(1, len(items)):
        prev = float(items[index - 1].get("score") or 0.0)
        cur = float(items[index].get("score") or 0.0)
        if cur > prev + EPS:
            return {"ok": False, "detail": f"score 非降序: rank{index}={prev:.6f} < rank{index + 1}={cur:.6f}"}
    return {"ok": True, "detail": "score 单调非增、rank 连续"}
```

两个巧思：

1. **`ranks != list(range(1, len(items) + 1))`**：一行同时检查「从 1 开始」
   「连续」「不多不少」。比较 `[1,2,3] != [1,2,3]` 为 False → 通过。
   如果 `ranks = [1, 3, 4]`，`range` 生成 `[1,2,3]`，不相等 → 报错。
2. **`cur > prev + EPS`**：浮点数不能用 `==` 比较（`0.1+0.2 != 0.3`）。
   `EPS = 1e-12`（`rag_metrics.py:26`）是容差。
   注意这里只判 `>`（严格大于才算错），所以**相等是允许的**（单调非增）。

```python
def check_tie_by_doc_id(hits):
    """分数并列时必须按 doc_id 升序（稳定、可预期的次序）。"""
    items = list(hits or [])
    for index in range(1, len(items)):
        prev, cur = items[index - 1], items[index]
        same_score = abs(float(prev.get("score") or 0.0) - float(cur.get("score") or 0.0)) < EPS
        if same_score and str(prev.get("doc_id")) > str(cur.get("doc_id")):
            return {"ok": False, "detail": (...)}
    return {"ok": True, "detail": "并列分数按 doc_id 升序"}
```

**为什么「并列时按 doc_id 排序」值得单独一条断言？**
因为搜索引擎里「分数相同」很常见（比如两个文档词频完全一样）。
如果没有稳定的 tie-break，同样的查询每次返回的顺序可能不同 —— **不可复现**，
那所有基于顺序的断言都会随机失败。所以这不是洁癖，是可测试性的前提。

```python
def find_duplicate_hits(hits) -> List[str]:
    """返回在 hits 中重复出现的 doc_id（去重缺陷证据）。"""
    seen: Dict[str, int] = {}
    for doc_id in doc_ids_of(hits):
        seen[doc_id] = seen.get(doc_id, 0) + 1
    return [doc_id for doc_id, count in seen.items() if count > 1]
```

`seen.get(doc_id, 0) + 1` 是「计数」的经典写法（等价于 `collections.Counter`）。

#### 8.3.6 8 种 RAG 断言一览（`nodes.py:305-355` + `models.py:27-39`）

| 断言类型 | 判据 | 失败说明什么 |
| --- | --- | --- |
| `rag_hits_include` | hits 里必须包含 `doc_ids` 指定的每个文档 | 召回缺失（或分词坏了） |
| `rag_rank_monotonic` | rank 连续 1..n 且 score 单调非增 | 排序逻辑 bug |
| `rag_tie_by_doc_id` | 分数并列时 doc_id 升序 | 缺稳定 tie-break |
| `rag_no_duplicate` | 同一 doc_id 不重复出现 | 多词项分数未聚合 |
| `rag_recall_at_least` | recall@k ≥ threshold | 召回质量差 |
| `rag_mrr_at_least` | MRR ≥ threshold | 相关文档排太后面 |
| `rag_no_ghost_hit` | 已删除文档不得被召回 | **陈旧索引**（索引没跟语料同步） |
| `rag_status` | HTTP 状态码符合契约 | 契约不符 |

#### 8.3.7 真实缺陷长什么样（本机实跑的 `RAG-006`）

```text
[executor] FAIL RAG-006 文档删除后不应再被召回（索引与语料一致）
  (期望 HTTP 200；已删除文档不再被召回
   / 实际 删除后检索 hits=['DOC-EN-002', 'DOC-PROBE-TMP', 'DOC-PROBE-TMP']，
     ghost=['DOC-PROBE-TMP', 'DOC-PROBE-TMP']，
     index_size=12/corpus_size=11 / 63ms)
```

读法：
- `DOC-PROBE-TMP` 是探针文档（第 5.4 节讲的）。
- 它**已经被删除**了，但检索还能返回它两次 → 说明索引里还留着旧数据 → 陈旧索引。
- `index_size=12` 但 `corpus_size=11` → 索引比语料多一篇 → 交叉验证同一结论。

**这句话就是一份可复核的缺陷报告**：说清期望、实际、证据，任何人都能照着复现。

### 9.3 MockBrain 的归因规则链（`mock_brain.py:316-415`）

`analyze_failures` 是一条 if/elif 链，**顺序至关重要**：

```python
for r in results:
    if r.ok: continue                            # 通过的跳过
    if r.invalid_case:                           # ① 用例自己写错
        → category="test_issue", severity="low"
    elif r.actual_status == 0:                   # ② 完全没响应
        → category="environment", severity="high"
    elif r.kind == "rag":                        # ③ 检索类失败
        → self._rag_defect(...)                  #    再细分成 5 种
    elif "400" in r.expected and r.actual_status == 500:   # ④ 契约：400→500
        → category="contract"
    elif "400" in r.expected and r.actual_status == 200:   # ⑤ 校验缺失：400→200
        → category="bug"
    elif r.actual_status == 503 or "temporarily unavailable" in r.evidence:  # ⑥ 不稳定
        → category="flaky"
    else:                                        # ⑦ 兜底
        → category="test_issue"
```

**为什么要这个顺序？** 看 ① 和 ② 的注释：

```python
# ① mock_brain.py:327-330
if r.invalid_case:
    # 用例本身不成立（例如把 RAG 专用断言写进了 API 用例）。它必须先于下面
    # 所有业务分支被判掉：请求可能明明成功了，却因为断言类型不存在被记成
    # FAIL。归因成 bug/contract 会让报告凭空多出一个不存在的被测缺陷。

# ② mock_brain.py:344-347
elif r.actual_status == 0:
    # 没有拿到任何 HTTP 响应（连不上、超时、连接被重置）。这类失败与被测
    # 逻辑无关，必须先于下面的业务分支判掉：否则「服务根本没起来」会被
    # 归因成「契约不符」或「召回质量差」，报告把环境故障写成被测缺陷。
```

**这两条注释是「归因顺序」的教科书级示例**：

> 归因是在「解释失败」。当有多种解释都成立时，
> **必须先排除「与被测系统无关」的原因**（用例写错、环境挂了），
> 再讨论「被测系统的业务问题」。

否则你会得到一个荒谬的结论：「服务没启动 → 所以它契约不符」。
顺序错了，报告会捏造缺陷 —— 这是比漏报更严重的错误（误报会消耗排查人力）。

```text
API: AgentTest Demo API v1.0.0
  GET    /api/health  -> 200
  POST   /api/login  -> 200, 400, 401  params=[requestBody{username:string, password:string}]
  GET    /api/todos  -> 200, 400  params=[query:status]  (列出待办)
```

**三个好处**：
1. **省 token**：完整 openapi.json 可能几千行，摘要后 20 行。
2. **给 LLM 需要的，不给噪音**：LLM 需要的是「路径 + 方法 + 可能的响应码 + 参数」，
   不需要 `$ref`、`components.schemas` 的层层嵌套。
3. **可读性**：人也能一眼看懂，方便调试提示词。

#### 9.5.2 `_describe_request_body`：一个「填错值」引发的思考

```python
# spec_tool.py:38-61（节选）
def _describe_request_body(req):
    """把 requestBody 压缩成 `{prop:type, ...}` 加示例值。

    只写 `requestBody` 三个字是不够的：实测真 LLM 生成的登录用例会把
    password 填成 `"password"` 字面量，拿到 401 后归因出一个**根本不存在的**
    「鉴权链路异常」缺陷。schema 里有什么字段、example 用什么值，是判断
    「接口坏了」还是「我不知道正确的输入」的唯一依据，必须交给它。
    """
```

这是项目里最好的「真实踩坑」案例之一：

```text
契约里写了：requestBody = {username: string, password: string}
若只给 LLM 看 "requestBody" 这几个字：
    LLM 猜 → body = {"username": "user", "password": "password"}   ← 字面量 "password"
    实际 → 401（因为正确密码是 123456）
    归因 → "鉴权链路异常"（一个根本不存在的缺陷）
```

**这个坑的教训**：LLM 不是「不聪明」，是「**没给它必需的信息**」。
`example` 字段就在契约里，摘出来给它就能解决。**这是提示词工程的典型工作。**
所以 `_describe_request_body` 不但给字段名和类型，还专门找 `media.example` /
`schema.example` 拼在末尾：

```python
example = media.get("example") or schema.get("example")
if isinstance(example, dict) and example:
    pairs = ", ".join(f'"{k}":"{v}"' for k, v in example.items())
    text += " 示例=" + "{" + pairs + "}"
```

### 9.6 降级：失败也要「说出来」

```python
# llm_brain.py:276-298
def _fallback_plan(self, context, reason):
    """LLM 调用失败或输出为空时兜底，保证流程不中断。

    兜底本身是设计的一部分，但"降级"必须显式可见——静默降级会让报告里的
    `brain_name=llm` 变成谎言。所以这里把 reason 写进日志，并由调用方
    （planner 节点）把它带进 trace 与报告。
    """
    from agenttest.brain.mock_brain import MockBrain
    logger.warning("[llm_brain] 降级为 MockBrain：%s", reason)
    self.last_fallback_reason = reason          # ← 关键：留下证据
    return MockBrain().make_plan("fallback", {}, context)
```

降级的证据链走三站：

```text
llm_brain.last_fallback_reason = "LLM 调用失败（APITimeoutError: ...）"
        ↓ planner 读它
state["context"]["brain_fallback_reason"] = reason
        ↓ reporter 读它
TestReport.brain_fallback_reason = "..."
        ↓ 模板读它
report.html 顶部出现一条黄色警告条（html_report.py:62-67）：
  ⚠️ 本轮配置了 LLM，但调用失败，规划与归因已降级为规则引擎（MockBrain）。
     报告中的用例与缺陷来自规则引擎，不代表大模型的输出。原因：...
```

**为什么这件事必须做到报告里，而不只是写个日志？**
因为报告是给人看的最终产物。如果只在日志里写「降级了」，
看报告的人（可能根本不会去看日志）就会把规则引擎的输出当成 LLM 的输出，
从而高估这个系统的能力。

> **通用原则**：**降级可以发生，但降级不能被隐藏。**
> 一个诚实的「我退化了」好过一个漂亮的「我假装没退化」。

### 9.7 `_resolve_related_case_ids`：修一个「关联退化成噪声」的 bug

```python
# llm_brain.py:168-204
def _resolve_related_case_ids(declared, failed, endpoint):
    """把 LLM 自报的 case_ids 变成可信的关联用例列表。

    旧实现给每个缺陷挂上本次**全部**失败用例，于是「检索排序缺陷」也关联着与它
    毫无关系的契约用例——关联退化成噪声：报告里每个缺陷那一栏都一模一样。
    """
```

三步处理：

| 步骤 | 做法 | 为什么 |
| --- | --- | --- |
| ① 白名单过滤 | 只保留「本次真的失败过」的 case_id | LLM 会**编造**不存在的 id |
| ② 自报有效就用 | 保留 LLM 的语义判断 | LLM 有时判得比规则准 |
| ③ 自报为空时不退回全部 | 收窄到「同 kind 的失败用例」 | 挂全部 = 关联退化成噪声 |
| ③' kind 也无从判断时 | **留空** | 「关联未知」好过「关联是错的」 |

第 ③' 条是这个函数最成熟的判断（`llm_brain.py:180-181`）：

> 空列表是「关联用例未知」，错挂是「关联用例是错的」。

**这句话值得记一辈子**：在不确定时，输出「我不知道」比输出一个错误的答案好。
错的答案会让人去错误的地方排查，代价是「不知道」的好几倍。

### 10.2 `_load_dotenv`：25 行的「迷你 dotenv」

```python
# config.py:63-85
def _parse_dotenv_text(text: str) -> Dict[str, str]:
    """解析 dotenv 文本为键值对；忽略空行与 `#` 注释。"""
    values = {}
    for raw in text.splitlines():
        line = raw.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue                          # 跳过空行/注释/非法行
        key, _, value = line.partition("=")   # 只在第一个 = 处切分
        key = key.strip()
        value = value.strip().strip('"').strip("'")   # 去掉引号
        if key:
            values[key] = value
    return values

def _load_dotenv(path=None) -> None:
    """轻量 .env 加载：已存在的环境变量优先，不覆盖。"""
    path = path or Path(".env")
    if not path.exists():
        return
    for key, value in _parse_dotenv_text(path.read_text(encoding="utf-8")).items():
        if key not in os.environ:            # ← 关键：不覆盖已有的
            os.environ[key] = value
```

**为什么不用 `python-dotenv` 这个现成库？**
因为只需要 25 行，加一个依赖不值得（项目对依赖数量很克制，
`requirements.txt` 只有 8 个包）。这也是一个工程判断：**能 25 行写完的，
不要引入一个库。**

**`line.partition("=")` 的巧思**：`"A=B=C".partition("=")` → `("A", "=", "B=C")`。
只在**第一个**等号处切分，所以值里可以包含等号（比如 base64 字符串、URL 的 query）。
如果用 `line.split("=")` 就会切成 3 段然后崩掉。

**`if key not in os.environ` 的语义**：`.env` 的优先级**低于**真实环境变量。
所以 CI 里 `export AGENTTEST_LLM_MODEL=gpt-4o` 能覆盖 `.env` 里的值 ——
这在「本机用 deepseek，CI 用别的模型」时很有用。

```python
# config.py:88-101
def resolve_env_name() -> str:
    name = _env("AGENTTEST_ENV", DEFAULT_ENV).lower() or DEFAULT_ENV
    if name not in KNOWN_ENVS:                      # KNOWN_ENVS = ("dev","staging","prod")
        raise ValueError(f"未知的 AGENTTEST_ENV={name!r}，可选值：{' / '.join(KNOWN_ENVS)}")
    return name

def load_profile(env_name: str) -> Dict[str, str]:
    profile_path = PROFILE_DIR / f"{env_name}.env"   # scripts/env/<name>.env
    if not profile_path.exists():
        return {}                                     # 文件缺失 → 回落到代码默认值
    return _parse_dotenv_text(profile_path.read_text(encoding="utf-8"))
```

**「写错值就直接 `ValueError`」是刻意的**（`README.md:487` 的说法：
*明确报错优于静默跑错环境*）。
如果写错 `AGENTTEST_ENV=stagng` 却静默用 dev，你会以为在测预发环境，
实际测的是本机 —— 又是「假执行」。

**`if not profile_path.exists(): return {}`** 也是刻意的：
档案文件缺失不报错，直接回落到代码默认值。这样「删掉档案文件」也能跑，
只是失去分层能力。这是「渐进增强」而不是「硬性依赖」。

### 10.4 「环境无感」原则：全项目最重要的工程教训

这个原则在项目里出现了 **4 次**，每次都有实测证据。它是这个项目最有「实战味」的部分。

#### 10.4.1 问题：代理环境变量会污染测试结论

假设你的机器上设了代理（公司网络下很常见，形如
`HTTP_PROXY=http://127.0.0.1:7897`）。`requests` 库**默认会读这些环境变量**，于是：

```text
测 127.0.0.1:5001 的请求 → 被交给代理 → 代理说"我不转发本地地址" → 502
                                    ↓
                        测试结论：被测系统返回 502（缺陷！）
```

但被测系统根本没问题，它甚至没收到这个请求。

#### 10.4.2 项目里的四处修正

| 位置 | 代码 | 防的是什么 |
| --- | --- | --- |
| `runner.py:74` | `session.trust_env = False` | 健康检查被代理劫持 → 误判「服务起不来」 |
| `api_tool.py:30` | `session.trust_env = False` | API 测试请求被代理劫持 → 误报 502 缺陷 |
| `spec_tool.py:30` | `session.trust_env = False` | 读契约被代理劫持 → 读回代理的错误页 |
| `llm_brain.py:59` | `httpx.Client(trust_env=False)` | LLM 链路被代理影响（见下） |

`api_tool.py:11-31` 的注释记录了实测证据，值得完整读一遍：

> **实测（2026-10-19，本机导出 `HTTP_PROXY=http://127.0.0.1:7897`）**：
> `tests/test_api_tool.py::test_network_error_reported` 与
> `tests/test_rag_tool.py::test_rag_search_tool_reports_network_error`
> 这两条**专门钉「网络错误被如实报告」的用例**在带代理时红、去掉代理即绿。
>
> 这是最讽刺的一类失败：验证「错误被正确报告」的用例，被一个环境变量
> 变成了「报告了一个不存在于被测系统的错误」。**工具链自己的传输层必须先
> 对环境无感，否则所有基于它的判断都只在这个 shell 里成立。**

**「所有基于它的判断都只在这个 shell 里成立」** —— 这句话是整个原则的核心。
如果工具受环境影响，那么「通过/失败」就不再是可复现的事实，而是「你机器上的现象」。
那这个工具的所有结论都失去了意义。

#### 10.4.3 LLM 链路的「代理 → 崩溃」：一个更离奇的案例

`llm_brain.py:23-59` 的 `_direct_httpx_client` 注释是全项目最长的一段，
因为它踩的是一个**在构造阶段就崩**的上游 bug：

```text
httpx 0.28.1 的 get_environment_proxies() 解析 NO_PROXY 时：
  对每个条目先判 is_ipv4_hostname / is_ipv6_hostname
  `[::1]`（带方括号的 IPv6，curl 明确支持的写法）两个都返回 False
  → 落进 else 分支，被当域名拼成 all://*[::1]
  → URLPattern 解析时把 "1]" 当端口
  → 抛 InvalidURL: Invalid port: ':1]'
  → 而这发生在 httpx.Client(...) 构造时
  → 所以 ChatOpenAI(...) 连实例都造不出来（请求都还没发）
```

实测对照表（`llm_brain.py:36-40`）：

| `NO_PROXY` 内容 | 结果 |
| --- | --- |
| `...,::1,...` | ✅ 正常（`is_ipv6_hostname('::1')` 为真） |
| `...,[::1],...` | ❌ `InvalidURL: Invalid port: ':1]'` |
| `URLPattern('all://[::1]')`（直接测） | ✅ 正常 |
| `URLPattern('all://*[::1]')`（实际走的路径） | ❌ 崩 |

**为什么不要求用户「把 `[::1]` 从 NO_PROXY 里删掉」？** 注释回答得很干脆：

> 那是合法规避写法，而且 `NO_PROXY` 常常是公司/工具自动注入的（本机就是 DSH 宿主
> 注入的），期望每个使用者手工清理，等于让代码对环境敏感。

**这就是「设计选择」与「甩锅给用户」的分界**：如果修法要求用户改环境，
那这个 bug 会在每个新机器上重现一次。把它修在代码里，只修一次。

#### 10.4.4 代价也要说清（`llm_brain.py:49-53`）

```python
# 代价要说清：设了 trust_env=False 之后，确实需要走代理才能出网的机器会连不上。
# 所以给了一个显式逃生口 AGENTTEST_LLM_HTTP_PROXY：需要走代理就显式填地址，
# 不填就是直连。刻意不自动继承环境变量 —— 自动继承正是这个缺陷的来源。
# 取舍是：一次 InvalidURL 崩溃比「本机该走代理没走」更难排查，
# 因为前者长得像代码 bug，后者报的是连接超时。
```

**注意这段的思维方式**：
1. 承认代价（有些机器会连不上）；
2. 提供显式逃生口（配一个环境变量）；
3. **解释为什么这个取舍是对的**（哪种错误更难排查）。

> **面试可以这么讲**：「我的原则是『显式优于隐式』。
> 自动读环境变量看着方便，但它把『环境问题』伪装成『代码 bug』。
> 所以我让工具默认对环境无感，需要特殊网络环境时显式配置 ——
> 这样报错信息永远和真实原因对应得上。」

### 10.5 `_find_chrome`：跨平台探测的三层策略


### 11.1 为什么需要一个「故意有 bug」的系统

### 11.3 `TodoStore`：三个并发安全细节

```python
# app.py:42-93（节选）
class TodoStore:
    """线程安全的内存存储。"""
    def __init__(self):
        self._lock = threading.Lock()
        self._next_id = 3
        self._todos = {1: {...}, 2: {...}}

    def list(self, status=None):
        with self._lock:
            items = list(self._todos.values())     # ← 在锁内拷贝
        if status:                                  # ← 在锁外过滤
            items = [t for t in items if t["status"] == status]
        return items

    def get(self, todo_id):
        with self._lock:
            return self._todos.get(todo_id)         # ⚠️ 返回的是引用，不是拷贝

    def create(self, title, priority="medium"):
        with self._lock:
            todo_id = self._next_id
            self._next_id += 1                      # ← 自增在锁内（否则会撞 id）
            todo = {...}
            self._todos[todo_id] = todo
            return todo
```

三个关键点：

1. **`self._next_id += 1` 必须在锁内**。这是非原子操作（读 → 加 → 写），
   两个请求同时进来会拿到同一个 id。虽然 Python 有 GIL，但 `+=` 中间可能切换线程。
2. **`list()` 在锁内 `list(...)` 拷贝，锁外过滤**。为什么？因为过滤可能慢，
   持锁时间越短越好；而且拷贝之后遍历是安全的（不受其他线程增删影响）。
3. **`get()` 返回的是字典引用，不是拷贝** —— 这是一个潜在的 bug（调用方改了会污染存储）。
   但在这个 demo 里没人改，所以没问题。**这正好是一个「可以拿来讲的代码审查点」**。

### 11.4 三个 API 缺陷的实现

#### 缺陷 1：`BUG-INVALID-STATUS-500`

```python
# app.py:30-35
VALID_STATUS = {"active", "done"}
BUG_INVALID_STATUS_500 = True          # ← 缺陷开关

# app.py:177-184
@app.get("/api/todos")
def list_todos():
    status = request.args.get("status")
    if status is not None and status not in VALID_STATUS:
        if BUG_INVALID_STATUS_500:      # 注入缺陷 1：契约要求 400，实现返回 500
            return jsonify({"error": "internal error: unexpected status filter"}), 500
        return jsonify({"error": "invalid status"}), 400
    return jsonify({"data": store.list(status), "count": len(store.list(status))})
```

**契约说**（`openapi.json`）：非法 `status` → 400。
**实现做**：返回 500。
**为什么这算缺陷而不算「差不多」**：400 是「你请求错了」，500 是「我服务器错了」。
客户端看到 500 会重试或报警，看不到「我该怎么改参数」。这是语义错误，不是小事。

#### 缺陷 2：`BUG-EMPTY-TITLE`

```python
# app.py:186-199
@app.post("/api/todos")
def create_todo():
    data = request.get_json(silent=True) or {}
    title = (data.get("title") or "").strip()
    priority = (data.get("priority") or "medium").strip().lower()
    if priority not in VALID_PRIORITY:
        return jsonify({"error": "invalid priority"}), 400
    if not title:
        if BUG_EMPTY_TITLE:     # 注入缺陷 2：契约要求 400，实现返回 200 且创建脏数据
            todo = store.create(title or "(empty)", priority)
            return jsonify({"data": todo, "warning": "created with empty title"}), 200
        return jsonify({"error": "title is required"}), 400
    todo = store.create(title, priority)
    return jsonify({"data": todo}), 201
```

**契约说**：空 `title` → 400。
**实现做**：返回 200，并且**真的把脏数据写进了存储**（`title or "(empty)"`）。
**为什么这是最严重的一类缺陷**：它不只是返回了错的状态码，而是**污染了数据**。
报告里会写「（脏数据已写入）」（`mock_brain.py:384`）—— 这句话是对的。

#### 缺陷 3：`FLAKY-001`

```python
# app.py:225-229
@app.get("/api/flaky")
def flaky():
    if random.random() < 0.1:      # 注入缺陷 3：不稳定服务（10% 概率 503）
        return jsonify({"error": "service temporarily unavailable"}), 503
    return jsonify({"flaky": True, "ok": True})
```

**这是「用来测测试工具」的缺陷**：它考验的不是 Agent 能不能发现它，
而是**Agent 的重试机制设计得好不好**。

| 设计 | 结果 |
| --- | --- |
| 不重试 | 10% 概率误报 flaky 缺陷 |
| 只内层重试 3 次 | 0.1% 概率误报 |
| 内层 3 次 + 外层补跑 1 轮 | 0.0001% 概率误报 |

**这个缺陷是「故意造出来验证你自己的重试逻辑」的**。一个成熟的测试系统
必须能区分「被测系统偶发故障」和「你自己的测试不稳定」。

```python
# demo_app/rag.py:54

```
这样测试可以同时验证两件事：
① 有缺陷时 Agent 能发现（默认 `RAG_BUGS` 全开）；
② 修好缺陷后 Agent 不误报（`CORRECT_BUGS` 全关）。

**这是「正反双向验证」**：只验证「能发现缺陷」不够，
还得验证「没缺陷时不会乱报」。

#### 实测指标（`docs/架构.md` 记录，由测试钉住）

| 实现 | recall@5 | MRR |
| --- | --- | --- |

### 11.6 `openapi.json`：项目的「宪法」

`demo_app/openapi.json`（8392 字节）定义了 11 个端点的契约：
路径、方法、参数、请求体 schema、可能的响应码、示例值。

**它有三个消费者**：

| 消费者 | 怎么用 |
| --- | --- |
| LLM（`brain/llm_brain.py`） | `summarize_spec()` 压成文本 → 进提示词 |
| 人（读代码时） | 「契约说 400」这句话的依据 |
| 测试（`tests/test_demo_app.py`） | 验证实现是否符合契约 |

**「契约即真相」是这个项目的世界观**：

```text
契约说 400，实现返回 500  →  缺陷（实现错了）
契约说 400，实现返回 400  →  正常
契约没写，实现返回 418    →  不是缺陷（契约没规定）
```

这个判断标准很重要：**不要用「我觉得应该怎样」来判缺陷，要用「文档说怎样」**。
否则测试会变成「测你个人的口味」。

### 12.3 三个「测试写法」值得学

#### 12.3.1 `xfail(strict=True)`：钉住「已知缺陷」

```python
# tests/test_demo_app.py:45-48（原文）
@pytest.mark.xfail(reason="注入缺陷 BUG-API-001：非法 status 应返回 400，实际 500", strict=True)
def test_invalid_status_should_be_400(client):
    r = client.get("/api/todos?status=invalid")
    assert r.status_code == 400
```

`xfail` 的意思是「预期会失败」。它有两个好处：

| 状况 | `strict=True` 的行为 | 意义 |
| --- | --- | --- |
| 测试真失败（缺陷还在） | 标记为 `xfailed`，**不报红** | CI 保持绿，同时记录了「这里有已知缺陷」 |
| 测试通过了（缺陷被修好了） | 标记为 `XPASS` 并**报红** | 提醒你「这条 xfail 该删了」 |

**这就是「缺陷台账」的代码化**：不写在 issue 里，写在测试里，
CI 每天帮你核对一遍「这个缺陷还在吗」。

#### 12.3.2 「钉住当前实际行为」

除了 xfail（钉「应该的样子」），还有一类测试专门钉「**现在的样子**」：

```python
# 摘录注释里的例子（docs/架构.md:105）
# 直接断言缺陷现状，如 assert ids == ["DOC-EN-001", "DOC-EN-001"]
```

这种测试看着奇怪（为什么要断言 bug？），其实很有用：
**缺陷被修复时它会红**，提醒你「行为变了，去看看是有意修的还是意外引入的」。

两种钉法配合起来，缺陷的「存在」和「消失」都能被感知到。

#### 12.3.3 「制造真环境」而不是 mock 一切

```python
# tests/conftest.py:13-23
```

### 12.4 覆盖率门禁：两层的设计

```toml
# pyproject.toml:176  —— 仓库级门槛
[tool.coverage.report]
fail_under = 70

# pyproject.toml:135-158 —— per-file 门槛（由 scripts/check_coverage.py 读）
[tool.coverage.perfile]
fail_under = 60
min_statements = 10
exclude = []
```

**为什么需要两层？** `pyproject.toml:141-145` 给出了一个真实例子：

> 下面 `[tool.coverage.report]` 的 `fail_under = 70` 是**仓库级**门槛，
> 结构上看不见单点失守。本仓活证据就是 `agenttest/runner.py` ——
> 126 语句 / 34 分支，**原先 0% 覆盖**，而总覆盖率仍有 76.88%、照样高于 70。
> 也就是说：把这套系统的**主入口**整个删掉，70 这道门禁也不会响。

**这就是「平均值陷阱」**：总覆盖率 76% 看着不错，但里面可能有一个 0% 的文件
（而且恰好是最重要的那个）。per-file 门槛专门堵这个洞。

而 `min_statements = 10` 是「小文件豁免」：3 行文件的百分比噪音太大
（少测一行就是 66% → 33%）。这一条也解释得很清楚。

## 第 14 章 常见困惑问答

### Q1：节点之间是怎么传数据的？我明明没看到节点互相调用

**答**：它们确实不互相调用。**它们只和「state」打交道。**

```python
def planner(state): ...
def executor(state): ...
```

LangGraph 在中间做转发：

```text
state ──► planner(state) ──► {"cases": [...]}  ──合并进──► state'
state' ──► executor(state') ──► {"results": [...]} ──合并进──► state''
```

这叫「**共享状态模式**」或「黑板模式（blackboard）」。好处是加节点不用改其他节点。
坏处是「谁改了 state 的哪一部分」需要靠约定（所以 `AgentState` 的类型定义很重要）。

### Q2：`trace` 为什么每个节点都返回？不重复吗

**答**：不重复。因为 `trace` 声明了 `Annotated[List[str], add]`（见 7.2），
LangGraph 会**拼接**而不是覆盖。如果换成普通 `List[str]`，那后一个节点会覆盖前一个，
最后只剩一行。

### Q3：为什么 `executor` 里会有 `while True`？不怕死循环吗

**答**：有三个 break 条件（见 6.2），其中 `attempts >= cfg.max_attempts` 保证必退出。
`while True` + 显式 break 是「重试循环」的标准写法，比 `for i in range(3)` 更好读 ——
因为「什么时候停」的判断条件写在中间，而不是靠循环变量。

### Q4：`brain.make_plan` 返回的用例，万一格式不对怎么办

**答**：不会。因为返回类型是 `List[TestCase]`，而 `TestCase` 是 Pydantic 模型：

- MockBrain 里是 `TestCase(...)` 直接构造 —— 字段错了立刻报错；
- LLMBrain 里 `with_structured_output(_PlanResult)` 保证 LLM 输出被解析成
  `_PlanResult`，字段类型不对时 LangChain 会重试或抛异常，最后走 `_fallback_plan`。

**这就是为什么用 Pydantic 而不是 dict**：在「进入系统」的那一刻就把格式错挡住。

### Q5：如果 LLM 一次生成 100 条用例会怎样

**答**：会跑很久，但不会崩。不过提示词里明确约束了（`llm_brain.py:90`）：

```text
6. 输出 12~20 条用例
```

**为什么要限制条数？** 因为 LLM 的输出有 token 上限。如果它生成 100 条，
JSON 可能被截断，然后**整份计划作废**（解析失败 → 降级 MockBrain）。
提示词第 7 条还专门叮嘱「字段字面量必须短」：

```text
7. **字段字面量必须短**：body / query 里任何字符串都不许超过 200 字符。
   要测超长输入时，写一个有代表性的短值（例如 "A" * 256 就写 256 个 A），
   不要原样铺开几千字符——那会把你的输出顶到 token 上限，JSON 被截断后整份计划都会作废
```

**这是提示词工程里很实际的一课**：你要主动防止 LLM 用「笨办法」把输出撑爆。

### Q6：报告里的 `category` 有 6 种，什么时候用哪个

**答**（`models.py:107`）：

| category | 含义 | 什么时候用 |
| --- | --- | --- |
| `bug` | 实现错误 | 状态码对了但数据错了、逻辑错了 |
| `contract` | 与契约不符 | 契约说 400，实现返回 500 |
| `flaky` | 不稳定 | 偶发 503，重试多次仍失败 |
| `environment` | 环境问题 | 完全没拿到响应（连不上/超时） |
| `test_issue` | 用例本身的问题 | 断言类型用错了、用例写错了 |
| `relevance` | 检索质量缺陷 | recall/MRR 不达标、排序错、陈旧索引 |

**为什么要把 `environment` 和 `test_issue` 单列出来？**
因为它们**不是被测系统的缺陷**。如果把「服务没启动」报成 `bug`，
开发会去代码里找一个不存在的 bug。分类的价值就在于「让对的人去看」。

### Q7：为什么 `demo_app` 里 `BUG_EMPTY_TITLE = True`，而不是直接从代码里删掉正确分支

**答**：因为**开关式**比**删除式**好一万倍：

| | 开关（`if BUG_XXX:`） | 删除正确代码 |
| --- | --- | --- |
| 验证「有缺陷时能发现」 | ✅ 开关打开 | ✅ |
| 验证「没缺陷时不误报」 | ✅ 开关关掉 | ❌ 得改代码 |
| 读代码时能看出「这是故意的」 | ✅ 一眼看出 | ❌ 看着像真 bug，会有人去"修" |

项目里还有 `CORRECT_BUGS = {k: False for k in RAG_BUGS}`（测试用），
就是「一键全关」造一个完美实现做对照组。

### Q8：如果我想加第 6 个节点，比如「发通知」，怎么加

**答**：三步，全在 `build.py`：

```python
# ① 写节点函数（nodes.py 或新文件）
def make_notifier(cfg):
    def notifier(state):
        # 读 state["defects"]，发个 webhook
        return {"trace": [f"[notifier] 已通知 {len(state['defects'])} 个缺陷"]}
    return notifier

# ② 注册节点（build.py:87 附近）
graph.add_node("notifier", make_notifier(cfg))

# ③ 改边：把 reporter 后面接上 notifier
graph.add_edge("reporter", "notifier")
graph.add_edge("notifier", END)      # 原来的 reporter → END 删掉
```

**注意**：如果要在 `state` 里存通知结果，得先在 `state.py` 的 `AgentState` 里加字段。
不需要的话（只写 trace），上面三步就够。

### Q9：`--no-ui` 之后报告里的 UI 用例哪去了

**答**：被 `planner` 过滤掉了（`nodes.py:39-43`）：

```python
if state["context"].get("skip_ui"):
    kept = [c for c in cases if c.kind != "ui"]
    trace = [f"[planner] {brain.name} 生成 {len(cases)} 条测试用例（--no-ui 过滤后 {len(kept)} 条）"]
```

**注意 trace 里会同时显示两个数字**（28 → 25），这样你知道「本来有 28 条，
我主动跳过了 3 条」，而不是「只有 25 条」。

**为什么在 planner 过滤而不是在 executor 跳过？**
因为过滤后的 `cases` 会影响到 `critic` 算覆盖率 —— 没跑的用例不应该算进覆盖率。
在 planner 阶段就砍掉，后面所有环节拿到的都是「本次真跑什么」。

### Q10：为什么我的报告里 `brain_name` 是 `llm`，但用例看着像规则生成的呢

**答**：看报告顶部有没有黄色警告条，或者看 `report.json` 里的 `brain_fallback_reason`：

```json
{
  "brain_name": "llm",
  "llm_configured": true,
  "brain_fallback_reason": "LLM 调用失败（APITimeoutError: ...）"
}
```

`brain_fallback_reason` 非空 = **本轮 LLM 挂了，实际用的是规则引擎**。
这正是 9.6 节讲的「降级必须可见」—— 不查这个字段你就被误导了。
