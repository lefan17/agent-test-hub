# 简历描述（项目经历话术）

> 本文所有数字均为本机实测（`reports/report.json` + pytest 原始输出），可复现。复现命令见每节末尾。

## 一句话版本

**Agent 自动测试系统**：基于 LangGraph + LangChain 的 API / UI / RAG 三覆盖智能测试平台，Agent 依据 OpenAPI 契约自动生成测试计划、执行与重试、归因缺陷并产出可视化报告；RAG 检索链路按「契约 + 不变量 + 质量指标」三层断言，产出 recall@k / MRR 可量化数值；可无缝切换规则引擎与真实 LLM 两种大脑。

## STAR 完整版

**S（背景）**：被测系统为 Flask 待办清单服务（契约驱动），面临接口回归成本高、UI 验证靠人工、问题定位慢的痛点；同时团队在推进 RAG 应用，但「检索效果变差」长期靠人工肉眼看结果，缺乏可回归的量化标准。

**T（任务）**：从零搭建一套 Agent 自动测试系统，覆盖 API 接口测试、Web UI 测试与 RAG 检索链路测试，能自动发现缺陷、量化检索质量并输出可审计报告。

**A（行动）**
- 用 LangGraph 编排四节点流水线：planner（生成测试计划）→ executor（执行+自动重试）→ critic（失败归因+覆盖率）→ reporter（HTML/JSON 报告）；
- 抽象 Brain 层：规则引擎 MockBrain（离线可跑、结果确定）与 LLMBrain（LangChain with_structured_output 结构化生成用例并归因缺陷），未配 Key 自动降级；
- 工具层保持确定性：requests 执行接口断言，系统 Chrome 无头模式做真实渲染断言与截图（另内置 Selenium 后端可切换），RAG 侧新增 `rag_search` / `rag_evaluate` 等工具；
- **RAG 检索链路测试**：在被测系统内实现纯标准库 BM25 检索引擎（不引入 rank_bm25 / jieba 等任何第三方依赖），把检索正确性拆成三层可断言对象——① 契约层（空 `q` / 非法 `top_k` 必须 400、响应结构、`index` 元信息）② 不变量层（rank 连续、score 单调非增、并列分数按 `doc_id` 稳定排序、同文档不重复、**删除后的文档不得再被召回**）③ 质量层（标注集算 recall@k 与 MRR）；
- **把「检索变差」变成数字**：把指标口径沉淀为 `agenttest/tools/rag_metrics.py` 纯函数（无 IO、无依赖），报告、测试、文档共用同一口径；新增 `Defect.category = "relevance"` 让检索失败归因到「相关性缺陷」而不是笼统的 `test_issue`；
- 失败重试与归因分离：5xx/网络错误指数退避重试 3 次，仍失败才进入归因，避免 Flaky 误报；
- 被测系统注入真实缺陷：API 侧 2 个契约缺陷开关 + 1 处 Flaky 注入，RAG 侧 6 个缺陷开关（覆盖召回 / 排序 / 去重 / 索引一致性 / 契约边界 5 个缺陷面），默认全开以复现；
- 为项目自身编写 180 项 pytest（161 passed + 15 项缺陷基准 xfail + 4 项需能启动的 Chrome 的 UI 用例）；另有 10 项 LLM 降级与缺陷关联回归、14 项评测集端到端阈值判定、8 项覆盖率端点映射一致性、2 项报告降级断言，钉住「LLM 调用失败必须降级并如实标注，而不是崩溃或伪装成真实 LLM」。

**R（结果）**
- 单次运行 28 条用例（15 API + 3 UI + 10 RAG），本机实测发现 14 个缺陷并按 4 类归因（5 contract / 2 bug / 4 relevance / 3 test_issue），`--no-ui` 路径 25 条用例发现 11 个缺陷（2 API + 9 RAG），本机墙钟约 8 秒；
- **检索质量可量化**：同一套 7 条标注查询下，注入缺陷的检索实现 recall@5 = **0.5714**、MRR = **0.5714**，正确实现两项均为 **1.0000**；差距全部来自 3 条中文查询召回为 0（中文分词缺陷）；另有 20 条评测集做端到端**阈值判定**（`recall@5 >= 0.8`、`MRR >= 0.8`）：缺陷实现 recall@5 = **0.7000** 判失败、正确实现 **1.0000** 判通过，评测集无标注或被测量缺失一律判失败；
- 报告含 Agent 思考轨迹、缺陷证据（请求原文 + 实际响应 + 期望 vs 实际）、覆盖率（API 端点 / UI 页面 / RAG 端点，RAG 按用例实际会打的端点展开）与 UI 截图（截图仅在 UI 用例跑通时产生），可直接交付业务方；
- 无 API Key 也能完整演示（MockBrain + 纯标准库 BM25），接入真实 LLM / embedding 后端只需配置环境变量；缺 Key、或 Key 配了但调用失败/输出畸形，都会自动降级为规则引擎，并在报告顶部显式标注降级原因（不会伪装成「真实 LLM」）。

## 投「软件测试工程师」版本（前 3 行重点）

> 接口自动化测试框架：以 OpenAPI 契约为基准自动生成正/反/边界/契约用例，覆盖 15+ 接口场景；
> 检索质量评测：对 RAG 检索链路做契约/不变量/指标三层断言，用 recall@k 与 MRR 把「检索效果」变成可回归数字（缺陷实现 0.5714 vs 正确实现 1.0000）；测得并定位 6 类检索缺陷（中文分词召回为 0、排序升序、并列次序不稳定、重复召回、删除后陈旧召回、契约未返回 400）；
> 缺陷管理：自动重试区分 Flaky 与真缺陷，失败自动归类（bug/contract/relevance/flaky）并生成含证据的缺陷报告；项目自身 180 项 pytest（161 passed + 15 缺陷基准 xfail）。

## 投「Agent 开发工程师」版本（前 3 行重点）

> LLM 应用落地：LangChain 结构化输出驱动 Agent 自动生成测试计划与缺陷归因，Prompt 工程化；
> Agent 架构：LangGraph 状态机编排 planner/executor/critic/reporter，Brain 抽象实现规则引擎与 LLM 无缝切换；executor 按用例类型（api/ui/rag）分派不同断言求值器；
> 工程化：确定性工具层（Tool 抽象）、可观测 trace、失败降级、指标口径单点定义、pytest 回归保障。

## 面试被追问时的口径（避免夸大）

- **「BM25 是你自己实现的吗？」** 是。纯标准库实现 idf + 词频饱和 + 文档长度归一，`demo_app/rag.py`，公式与参数（k1=1.5、b=0.75）都在代码注释里。中文分词用「字符 unigram + 相邻 bigram」的简化方案，不依赖词典。
- **「指标数字怎么来的？」** 7 条标注查询（4 英文 + 3 中文）跑 `build_report()`，k=5。数字全部可复现：正确实现 1.0000 是因为 7 条查询的标注文档都被排在第 1 位；缺陷实现 0.5714 = 4/7，缺口正好是 3 条中文查询。
- **「测试全绿吗？」** 161 passed + 15 xfailed（缺陷基准，属预期，不含 UI）。另有 `tests/test_ui_tool.py` 的 4 条 UI 用例需要**能真正启动**的 Chrome，单独跑 `tests/test_ui_tool.py` 即可覆盖；在禁止创建子进程的环境里这 4 条会失败（`crashpad OpenProcess 拒绝访问 (0x5)`），属环境限制，与改动无关。跳过它们的命令：`pytest --ignore=tests/test_ui_tool.py` → 161 passed, 15 xfailed, 0 failed。
- **「15 个 xfail 是什么？」** 注入缺陷的回归基准：用 `@pytest.mark.xfail(strict=True)` 包住「断言契约期望行为」的用例，缺陷存在则 xfail，缺陷被修好会 XPASS 报错提醒更新基准；另有「钉住当前实际行为」的用例直接断言缺陷现状。
