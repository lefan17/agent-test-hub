## 一句话版本

**RAG 检索质量评测 + 测试工程化**：在自建 Flask 靶场上用**纯标准库**实现 BM25 检索引擎
（倒排索引，k1=1.5 / b=0.75，中文 unigram+bigram 分词，零第三方检索库），把检索正确性
拆成「契约 + 不变量 + 质量」三层可断言对象并沉淀为纯函数口径；同一套 7 条标注查询下，
注入 6 类检索缺陷的实现 recall@5 = 0.5714、正确实现 1.0000，差距可定位到中文分词召回为 0。
配套 332 项 pytest、92.07% 分支覆盖、per-file 覆盖率门禁与 6 job CI。

## STAR 完整版

**S（背景）**：团队在推进 RAG 应用，但「检索效果变差」长期靠人工肉眼看结果，缺乏可回归的量化标准；
接口回归靠人工点，UI 验证靠肉眼，缺陷定位靠翻日志。三类问题本质上都是「没有可断言的量化对象」。

**T（任务）**：建一套能把「检索质量」和「接口/UI 行为」变成可回归数字的测试工程，
并配齐能让它长期活下去的工程化外壳（覆盖率门禁、CI、静态检查、依赖治理）。

**A（行动）**
- **自研 BM25，不用现成库**：`demo_app/rag.py:104-173` 用纯标准库实现倒排索引
  （`_postings: Dict[str, Dict[str,int]]`），idf 在 `rag.py:168`（`math.log(1.0 + (total - df + 0.5)/(df + 0.5))`），
  长度归一在 `rag.py:171`，参数 `K1=1.5 / B=0.75` 在 `rag.py:30-31`。**不引入 rank_bm25 / jieba / numpy**。
  中文分词走「字符 unigram + 相邻 bigram」（`rag.py:79-97`），无需词典。
- **指标口径沉淀为纯函数**：`agenttest/tools/rag_metrics.py` 里 recall@k / MRR 是无 IO、无依赖的纯函数，
  报告、测试、文档共用同一口径。**RR 的位次取 `enumerate` 下标，不采信被测方自报的 `rank` 字段**
  （`rag_metrics.py:95-110`）——注释写得很直白：「用被测方自报的位次去评被测方的排序质量，
  等于让它自己给自己打分」。这不是洁癖：`BUG_RAG_SORT_ASC` 恰好污染 rank 字段，采信它 MRR 会显示 1.0，
  把缺陷直接盖掉。
- **三层断言**：① 契约层（空 `q` / 非法 `top_k` 必须 400、响应结构、`index` 元信息）；
  ② 不变量层（rank 连续 1..n、score 单调非增、并列按 `doc_id` 升序、同文档不重复、**删除后不得再被召回**）；
  ③ 质量层（标注集算 recall@k / MRR）。
- **防假绿的几处硬设计**：标注缺失判**失败**而不是按「无可漏项」记满分
  （`nodes.py:297-303`、`308-314`）；未实现的 `check.type` 一律判失败
  （`_eval_rag_check` 末尾兜底 `ok=False`）；用例自己写错的打 `invalid_case=True` 单独分类，
  不混进缺陷归因（`nodes.py:163-164`）。
- **工程化外壳**：仓库级覆盖率 70% + **per-file 60%** 双重门槛（`scripts/check_coverage.py:110-136`，
  配置缺失退出 1 而非静默通过、`exclude` 每条路径校验真实存在）；6 job CI（测试+覆盖率 / mypy+ruff /
  容器构建冒烟 / 依赖漏洞扫描 / 提交规范 / 失败通知）；mypy 全绿、ruff 全绿。
- **图编排（配角，如实说明）**：LangGraph 编排 planner→executor→critic→reporter，
  executor 之后有一处**条件边**（还有 5xx/无响应失败且补跑轮次未用完 → 走 `retrier` 补跑一轮，
  只跑失败的用例、不重跑全量），`retrier → executor` 是真实回边。`Config.retry_rounds` 默认 1，
  刻意压低：轮次越多越像在用重试掩盖真缺陷。

**R（结果）**
- **检索质量可量化**：同一套 7 条标注查询下，注入缺陷的检索实现 recall@5 = **0.5714**、MRR = **0.5714**；
  正确实现两项均为 **1.0000**。缺口全部来自 3 条中文查询召回为 0（中文分词缺陷）。
  另有 20 条评测集做端到端阈值判定（`recall@5 >= 0.8`、`MRR >= 0.8`）：缺陷实现 0.7000 判失败、
  正确实现 1.0000 判通过；空标注与被测量缺失一律判失败。
- **测试与覆盖率**：332 项 pytest（`--collect-only` 口径），本机 `--ignore=tests/test_ui_tool.py` 实测全部通过、0 failed（15 条缺陷基线 xfail）；
  `TOTAL 1598 stmts / 446 branch / 92.07%`；per-file 门槛 16 个文件全部达标；mypy 24 源文件无问题；ruff 全绿。
- **在线报告那次运行**（2026-10-23，`Brain：llm（真实 LLM）`）：26 条用例（20 API + 2 UI + 4 RAG），
  18 通过 / 8 失败，发现 **5 个缺陷**（2 API + 2 RAG + 1 UI）——这是报告维度的用例数，
  与上面 332 条 pytest 用例是两个不同的计量对象。
- 无 API Key 也能完整演示（MockBrain + 纯标准库 BM25）；接入真实 LLM / embedding 后端只需配环境变量，
  缺 Key 或调用失败/输出畸形都自动降级为规则引擎并在报告顶部显式标注降级原因（不伪装成「真实 LLM」）。

> mypy/ruff 全绿；per-file 门禁脚本自带 25 条测试（配置缺失退 1、排除路径写错报错）。
> 缺陷发现：自建靶场注入 6 类检索缺陷 + 2 个 API 契约缺陷 + 1 处概率性 Flaky，
> 演示「发现缺陷」而非「跑一遍全绿」；失败重试与归因分离，Flaky 不误报成 Bug。

## 投「Agent 开发工程师」版本（前 3 行重点）

> LangGraph 状态机编排：五个节点（planner / executor / retrier / critic / reporter），
> executor 之后一处**条件边** + `retrier → executor` **回边**实现跨轮补跑，
> 补跑只针对 5xx/无响应失败、只跑失败用例、轮次上限 1——形状由 `tests/test_graph_edges.py` 8 条测试机器化守卫。
> Brain 抽象：规则引擎与 LLM（LangChain 结构化输出）可切换，未配 Key 自动降级并在报告显式标注；
> LLM 编造的 `case_id` 走白名单过滤，自报无效时收窄到同 kind 而不退回「挂上全部失败用例」。
> 确定性工具层 + 可观测 trace + 传输层 `trust_env=False`（绕开 httpx 对 `NO_PROXY=[::1]` 的 InvalidURL）。

## 面试被追问时的口径（避免夸大）

- **「BM25 是你自己实现的吗？」** 是。纯标准库实现，`demo_app/rag.py`，idf 在 `rag.py:168`、
  长度归一在 `rag.py:171`、`K1=1.5 / B=0.75` 在 `rag.py:30-31`。中文分词用字符 unigram + 相邻 bigram，不依赖词典。
- **「指标数字怎么来的？」** 7 条标注查询（4 英文 + 3 中文）跑 `build_report()`，k=5。
  正确实现 1.0000 是因为 7 条查询的标注文档都被排在第 1 位；缺陷实现 0.5714 = 4/7，缺口正好是 3 条中文查询。
- **「标注集是谁做的？有 κ 一致性吗？」**（**这题会问，务必诚实**）单标注者，我自定，没有第二标注者、没有 κ。
  这是这个评测集最大的效度威胁——所以我不敢说「recall@5 是绝对质量」，只能说「相对缺陷实现有差距」。
- **「你这个 Agent 能换到别人的系统上跑吗？」**（**这题也会问**）**不能**。`MockBrain.make_plan` 的
  `spec` 参数没被使用，28 条用例是硬编码模板。当前验证的是机制，不是可迁移性。要做的是让它真读
  `spec.paths` 生成用例——在「下一步」清单里，不是现在的能力。
- **「图里有几个 conditional edge？」** 现在有 **1 个**（`executor` 之后），另有一条回边
  `retrier → executor`，见 `agenttest/graph/build.py`，由 `tests/test_graph_edges.py` 守卫。
  **没有** checkpointer、没有 `interrupt`、没有 `Send`/subgraph——断点续跑与人工介入是下一步。
- **「测试全绿吗？」** `pytest --ignore=tests/test_ui_tool.py` → **0 failed（15 条缺陷基线按 xfail 计）**。
  15 项 xfail 是缺陷基准（`@pytest.mark.xfail(strict=True)`），属预期。另有 4 条 UI 用例需要
  **能真正启动**的 Chrome，在禁止创建子进程的环境里会失败（`crashpad OpenProcess 拒绝访问 (0x5)`），
  属环境限制。
- **「归因准确率多少？」**（**最该自证、但本项目确实没做**）没有度量。全仓无变异测试
  （mutmut / cosmic-ray），所以「Agent 把失败归到正确类别」的比例无从谈起。
  332 项 pytest 验证的是**代码正确性**，不是**判断质量**——这两件事不能混。
- **「`/api/flaky` 是你自己注入的吧？」** 是。README 里写明：注入面 9 个，8 个有人类 xfail 钉住，
  唯一人类零覆盖的是 `/api/flaky`，且是 10% 概率触发的。**别吹成「Agent 发现了人类没发现的 7 个缺陷」。**
