# 对第三方契约跑一遍：从「测自己写的服务」到「测陌生契约」

> 2026-10-25 · 目标 `https://petstore3.swagger.io/api/v3`（Swagger 官方示例服务，我们不控制它）
> 产物：[`docs/evidence/petstore/report.html`](evidence/petstore/report.html) / [`report.json`](evidence/petstore/report.json)
> 在线版：https://lefan17.github.io/agent-test-hub/petstore/report.html

## 为什么要做这件事

这个仓库原来所有的证据都有一个共同前提：**被测系统是我自己写的**（`demo_app/`
的待办清单服务，连缺陷都是我注入的）。这带来一个绕不过去的质疑：

> 「你的 Agent 只是学会了测你自己写的那套端点吧？换成一份陌生契约还行吗？」

这不是靠解释能消掉的质疑。契约驱动的价值只有在**别人的契约**上才成立，所以我加了一个
入口 `scripts/run_remote.py`：同一套 LangGraph 流程，target 换成公网上的第三方服务，
契约从对方 `/openapi.json` 现取，用例由 LLM 现场生成。

## 怎么跑

```bash
# 本机需要走代理才能出网时，代理是**显式参数**（不读 HTTP_PROXY）
python scripts/run_remote.py \
    --base-url https://petstore3.swagger.io/api/v3 \
    --proxy http://127.0.0.1:7897
```

配置真实 LLM 的方式与主流程相同（`AGENTTEST_LLM_API_KEY` 等），详见
[`操作指南.md`](操作指南.md)。跑完产物落在 `reports/petstore/`。

## 一次真实运行的结果

2026-10-25 12:16:00 → 12:16:36，**36 秒**，`brain_name = llm`、`llm_configured = true`、
`brain_fallback_reason` 为空：

| 用例 | 通过 | 失败 | 归因出的缺陷 |
|---|---|---|---|
| 20 | 16 | 4 | 4 |

13 个端点里覆盖到 9 个（`/pet`、`/pet/findByStatus`、`/pet/findByTags`、`/pet/{petId}`、
`/store/inventory`、`/store/order/{orderId}`、`/user/login`、`/user/{username}`、
`POST /pet/{petId}` 表单更新）。

### 三条它判成「对方契约没兑现」的

| 缺陷 | 现象 | 为什么算契约缺陷 |
|---|---|---|
| DEF-001 `high/contract` | `POST /pet` 不带 `name` / `photoUrls` 仍返回 200 并落库 | 契约把 `name`、`photoUrls` 标为 required，实现没校验 |
| DEF-002 `high/contract` | `POST /pet` 的 `status` 传 `notastatus` 被接受并持久化 | 契约列了 `available/pending/sold` 枚举，实现没校验 |
| DEF-003 `high/contract` | `GET /user/login` 不带凭据返回 200 并**建立了会话** | 契约要求 `username`/`password`，实现反而发了 session token |

这三条都不是"猜"出来的：每条都附了请求、期望、实际响应体（见报告证据列），
而且都能用 curl 手工复现 —— 换个人来跑，结论一样。

### 一条它自己判成「我的用例有问题」的

DEF-004 是 `GET /pet/1` 期望 200 实际 404，被标成 `test_issue`（不是 `bug`、不是 `contract`）：

> 「该用例依赖固定 id=1 的数据，而其他用例会创建新宠物，说明数据非自建」

这条比我预期的重要。**公共演示服务的数据不由我控制**，把"1 号宠物不存在"报成缺陷，
是最典型的假缺陷。critic 把它归到 `test_issue`，等于把"我不知道那是你的测试数据"
和"你的实现有问题"分开了 —— 这道分界线是这个项目最想证明的判断力。

## 这次才暴露出来的三个工程问题（都已修）

### 1. 提示词里的字面花括号会把 `.format()` 打崩

第一版我在 `SYSTEM_PLAN_PROMPT` 里写了「契约里写 `/pet/{petId}` 时，path 要写成
`/pet/1`」。而这份提示词是用 `str.format(spec=...)` 渲染的 —— `{petId}` 被当成
占位符，第一次运行直接崩在 planner：

```
KeyError: 'petId'
  at llm_brain.py:258  prompt = SYSTEM_PLAN_PROMPT.format(spec=summarize_spec(spec))
```

修法是双写花括号 `{{petId}}`，并在模板顶上留了注释。这个坑有价值的地方在于：
**它只在"契约里真的有路径参数"时才炸**，而本仓自家的 `demo_app` 端点恰好没有路径参数
—— 所以自测永远发现不了，一上陌生契约立刻现形。

### 2. `python scripts/x.py` 的 `sys.path[0]` 是 `scripts/`

```
ModuleNotFoundError: No module named 'agenttest'
```

同一个坑本仓库在 CI 上已经踩过一次（`python scripts/proxy_probe.py` 报
`No module named 'bench'`）。脚本里显式把仓库根插到 `sys.path` 前面。

### 3. 远端目标会被当成本机服务，然后**原地起一个本地 demo 继续测**

这是最危险的一个，因为它不报错。原 `runner.main` 的逻辑是「健康检查不过 → 起本地
`demo_app`」，而远端服务没有 `/api/health`，于是：

> 拿远端 base_url 跑 → 健康检查 404 → 判"服务没起来" → 起本地 demo → 测的是自己

流程全绿、报告很绿、被测对象却不是你以为的那个。修法是 `runner.is_local_target(url)`
按 hostname 判断，远端目标跳过健康检查与本地起服，能不能用由"契约读得到"来决定。

## 诚实边界（这几条必须一起说，否则上面的数字就变成吹牛）

- **Petstore 是演示服务**，它的实现本来就宽松（这也是它被当作反例教材的原因）。
  在上面发现契约缺陷，不代表这个 Agent 在真实业务系统上也能发现同样密度的缺陷。
- **20 条用例不是穷尽**：13 个端点里 9 个被覆盖，`/pet/{petId}` 的 multipart、
  `/user/createWithList`、`/store/order` 的创建链路都没覆盖。
- **LLM 生成是非确定的**：同一份契约两次跑，用例集不一样。所以这次结果写成
  "某一次运行的快照"（`docs/evidence/petstore/`），不当作可回归的固定集合。
- **它留了两条脏数据**：DEF-001/002 两个用例成功创建了 id `987654322`、`987654323`
  的宠物却没有删除（因为那两条用例的预期结果是 400，删数据的收尾步骤没被执行到）。
  公共环境上这属于不礼貌，但也是真实缺陷 —— 已记在这里，不假装没发生。
- **不作为 CI 阻塞步骤**：对方随时可能慢/挂/改，用例又非确定。把这种东西放进门禁，
  只会训练出"红了就重跑"的习惯。它是手工执行的证据，与主报告的 green badge 分开算。

## 复现

```bash
# 1) 同一个入口，同一份契约
python scripts/run_remote.py --base-url https://petstore3.swagger.io/api/v3 --proxy http://127.0.0.1:7897

# 2) 想核对某条缺陷？直接在 curl 里复现（以 DEF-003 为例）
curl -s "https://petstore3.swagger.io/api/v3/user/login" -H "accept: application/json"
# → Logged in user session: <一串数字>     ← 没传 username/password 也建了会话
```
